# Changelog

All notable changes to `precision-soft/melody/integrations/bunorm/v3` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `encrypt.EncryptedString.UnmarshalJSON`, `EncryptedDeterministicString.UnmarshalJSON`, `EncryptedStringFor[R].UnmarshalJSON` and `EncryptedDeterministicStringFor[R].UnmarshalJSON`, the read side of the redacting `MarshalJSON` the four column types already had: a plaintext string decodes as itself, a json null leaves the value untouched, and the redaction placeholder is refused rather than stored — the round trip that used to seal `<redacted>` over the secret is described under *Changed*
- `audit.ErrAsyncStorageQueueFull` and `audit.ErrAsyncStorageClosed`, the sentinels an `AsyncStorage.Save` wraps when it could not take an entry — the buffer was full, or the storage was already closed — so a caller can tell a lost audit record apart from a delegate failure with `errors.Is`
- `ManagerRegistry.SetLogger` replaces the logger a registry reports through and takes bun's diagnostic channel with it, so the two cannot drift apart. It exists for the wiring window an application cannot avoid: a registry assembled while the modules are still being wired has no application logger to be handed — the framework's own does not exist yet — so it is built on the emergency logger, and without this door every later open, every retry warning and every terminal connection failure kept bypassing the journal for the life of the process. A nil logger, and a typed nil holding no value, are refused with `ErrLoggerIsRequired`
- `ManagerRegistry.CloseMigrationDatabase(name)` ends the dedicated migration connection for one definition and forgets it, so the next `MigrationDatabase` for that name opens a fresh one. That connection is not a request pool and must not live like one: it deliberately lifts the driver's read and write deadlines and recycles nothing, which is right for a DDL statement that runs for minutes and wrong for anything that then sits idle — memoized until the registry itself closed, a single migration run at the boot of a process that goes on to serve requests kept a deadline-less connection open for that process's whole life. An empty name selects the default definition, a name with no migration connection is not an error, and a closed registry refuses it
- `ResetDiagnostics` hands bun's diagnostic channel back: the records go to standard error again, which is where bun writes them when nobody routes them at all. It is what a teardown calls while the logger it routed to is still alive, and it is the door for a process that hosts melody rather than being one
- `audit.NewRecorderOwningStorage` and `Recorder.Close`: the recorder built by hand over an `AsyncStorage` had a drain goroutine only the storage's `Close` ends, and a recorder registered as the sole service over it was a closable resource the container teardown could never reach. The default `NewRecorderWithStorage` deliberately does NOT own the storage — on the container path both are registered services and the container closes each one itself, so an owning default would close it twice
- `encrypt.EncryptedColumn`, the marker interface every encrypted column type implements — the two default-cipher forms and every instantiation of the two compartment-bound generic forms. A consumer that must recognise "a value of an encrypted column type" matches the interface rather than comparing types by identity, because each generic instantiation is a distinct `reflect.Type` no identity list can enumerate

- `ConnectionParameters.SafeContext` is pinned by its own mirror: it names the host, port, database and user, and the assertion that carries the guard is the negative one, which scans every value rather than only looking for the key it does not want — a password republished under another name reads as redacted to a check that asks only whether `password` is present. The same file pins that `ConnectionParams` is still an **alias** and has not become a defined type: nothing in this major's own tree spells the alias in the signatures that satisfy `Provider`, so the change would leave every in-tree build green while a provider outside the tree that spells it in those signatures silently stopped matching the contract

- `RouteDiagnostics` sends bun's own diagnostic channel to the application's journal, and the mysql and pgsql providers call it on their first open. Bun reports the developer's declaration mistakes through a package-level logger of its own — an unknown struct tag option, an unknown `on_update` or `on_delete` rule on a relation, a query carrying arguments and no placeholders — and unrouted they go to standard error as unstructured text, invisible to a deployment whose journal is a json file. They arrive as warning records under the message `bun diagnostic` with the line in the context, the shape `logging.NewStandardErrorLogger` already gives `net/http`'s own reporting. Bun's logger is one variable for the whole process, so the first provider to open wins it; a binary that never opens a database takes the setting at all. **Behavioural change** for anyone reading bun's warnings on standard error — see the framework's `UPGRADE.md`. One line is deliberately out of reach: the mysql dialect
  writes `can't discover MySQL version` through the **standard library's** default logger rather than bun's, so routing it would mean taking `log.SetOutput` for the whole process, which is the application's decision and not this package's — the mysql readme says how
- `MigrationContextOpener` — what `ContextOpener` is to `Open`: the migration open under the caller's context. The registry prefers it whenever a provider implements it, handing the context it was constructed with, exactly as it does for the ordinary open
- `ContextOpener`, the optional capability of opening under a caller's context, and `NewManagerRegistryWithContext`, which binds the registry to the context its lazy opens run under: a provider that implements the capability refuses an open the context already cancelled and has its retry sleeps watch the context alongside the clock — so a shutdown that cancels the context is honoured at every cancellable step of an attempt instead of sleeping through the whole retry budget, in the exact window supervisors send their signals. A nil context reads as `context.Background()`, the exact behaviour of `NewManagerRegistry`

- `MigrationProvider` is the optional capability of opening a connection tuned for migrations, and `ManagerRegistry.MigrationDatabase` answers it: the pool a provider opens for request traffic carries driver-level read and write deadlines sized for requests, and a legitimate DDL statement that runs past them — an ALTER TABLE adding constraints on a large table — is cut mid-statement with `invalid connection`, outside any transaction MySQL would roll back. A provider that implements the capability opens the same database with those deadlines lifted; the registry opens it once per definition, caches it beside the request pool — never inside it — and closes it on Close. A provider without the capability keeps the old behaviour: the ordinary pooled connection, reported as not dedicated

### Changed

- **Behavioural change**: `encrypt.NewStaticKeyProvider` refuses a key of 32 zero bytes, panicking at construction with the key id, as it already did for a key of the wrong length. All zero bytes is the key a buffer nobody wrote to has — a key file that was never generated, a variable that was never set, decoded and padded — and it sealed every column under a key any reader can guess, with nothing anywhere saying so. Nothing beyond that shape is judged: a key is the operator's, generated from `crypto/rand`, and the door cannot tell a strong one from a weak one
- **Behavioural change**: decoding a json document that carries the redaction placeholder into an encrypted column type is refused. `MarshalJSON` writes `<redacted>` where the plaintext was, and until now the four column types had no read side of their own, so `encoding/json` stored the placeholder as the value and the next `Value()` sealed `<redacted>` in place of the secret, with no error anywhere on the way — a document rendered by the application and posted back destroyed the secret it redacted. The new `UnmarshalJSON` (see *Added*) refuses the placeholder by name with the column type in the context, decodes any other string as the plaintext it is, and leaves the value untouched on a json null; the alternative, keeping the value on the placeholder, still empties a freshly decoded struct and seals the empty string, which is the same loss in silence — see the framework's `UPGRADE.md`
- **Behavioural change**: `audit.AsyncStorage.Save` reports an entry the queue could not take. It used to answer `nil` for an entry dropped on a full buffer or after `Close`, so the request path went on as if the audit record existed; it now dead-letters the entry as before and returns an error wrapping `ErrAsyncStorageQueueFull` or `ErrAsyncStorageClosed`, attempting every entry of the call and returning the first refusal. The caller is the one party still present when that entry is lost, and the queue protects the request path from the delegate's latency, not from knowing. A `Tracker` is unaffected: its saves carry a transaction binding and go through the delegate synchronously
- **Breaking** — the encrypt commands take `clicontract.Context` where they took `*clicontract.CommandContext`, following the framework's melody-owned flag and context layer; `github.com/urfave/cli/v3` is an indirect dependency of this module instead of a direct one. Nothing else about the commands changed — the framework's `UPGRADE.md` writes the rewrite out line by line

- **Behavioural**: the bulk migrator reads STORED values with the read side of the cipher's asymmetry, on both `mode=encrypt` branches. A stored marker-shaped value that no longer decrypts is a missing key or a truncated write, and both used to be re-sealed as if they were plaintext whenever the damage still parsed but failed authentication — destroying the only remaining copy; the run now stops on the row and names the key. The write-path leniency (an application string that merely looks like a marker) stays with the cipher's `Encrypt`
- **Behavioural**: `Migrator.MigrateEncrypt` and `MigrateReencrypt` run their own column-capacity check first. The check used to live only in the CLI command, so the programmatic caller — the path the package README recommends — ran with no width check at all and met exactly the silent truncation the check exists to prevent; the standalone `EnsureColumnCapacity*` doors remain for a caller that wants the answer without the run
- **Behavioural**: `audit.Change` marshals each side by PRESENCE rather than by emptiness. Under plain `omitempty` a genuine transition to a zero value — `active` true→false, a counter to 0, a string emptied — marshalled byte-identical to the one-sided shape of an insert or a delete, and a consumer of the trail could not tell "changed to false" from "no new value recorded". A present zero now renders (`"new":false`), an absent side stays out, and a `Change` built by hand keeps the old reading
- the `bun` requirement moves to `v1.2.17`, with the dialect and driver packages in lockstep: the dialects verify at init that their version equals bun's and panic otherwise. v1.2.16 swallowed the failure of a migration read from a `.sql` file, which `integrations/bunorm/migrate` answered with `[success]` and exit 0 over a schema that never changed; the whole family moves together so no binary can assemble a mismatched pair

### Fixed

- `encrypt.EncryptedDeterministicString`, `EncryptedDeterministicStringFor[R]` and the deterministic doors of the `Cipher` (`EncryptDeterministic`, `EncryptDeterministicWithKeyId`) convert a random-nonce seal in place instead of passing it through. The pass-through asked only whether a marked value authenticates under a key in the set, which is the whole question on the random doors but not on these: a seal written with a random nonce authenticates all the same, and a deterministic column that received one — a value copied over from a random column, or sealed through `Encrypt` before the column type changed — held a ciphertext `CiphertextCandidates` can never produce, so every equality lookup on that row answered no rows while the row held the plaintext. The value is now re-sealed deterministically under the key id it already carries, never under the door's, so the conversion is not a key rotation — the rule the bulk migration has applied to a stored column since its own repair; a seal that is deterministic already passes through whatever key it carries, so a retired key's ciphertexts survive until re-encryption exactly as on the random doors, which are unchanged
- `ReadWriteSplitter.Reader` refuses a replica whose provider answered neither a database nor an error instead of falling back to the primary. The registry refuses such a provider by name with `ErrProviderReturnedNilDatabase`, but the splitter's list of permanent failures did not know the sentinel, so every read of that replica went to the primary, forever and in silence — the wiring mistake the list exists to surface.
- `RouteDiagnostics` installs nothing when the logger is the one already routed, and a `ManagerRegistry.Close` hands bun's diagnostic channel back only when it is its own. Every provider open rebuilt the destination for the same journal, and a registry's teardown reset the process-wide channel unconditionally, so with two registries in one process — two applications in a test binary, a second registry wired beside the first — closing the first sent the second's diagnostics to standard error until its next open routed them again. `ResetDiagnostics` keeps handing the channel back whoever routed it, as the door of a host process.

- `audit.AsyncStorage` journals every dead-letter by default. Nothing installed a logger unless the composition root called `WithLogger`, and `deadLetter` returned at once on a nil one, so a full queue, a save after `Close`, a failing delegate and a panicking delegate all lost their entry with no record anywhere — the counters were the only signal, and nothing in the tree read them. A storage built by `NewAsyncStorage` now dead-letters through the emergency logger, the fallback the rate limiter and the database providers already take, until `WithLogger` replaces it
- `audit.AsyncStorage.Close` is bounded on every stretch. Past the drain grace it cancelled the worker's context and then waited for the worker without a bound, which only ends when the delegate reads that context: a `FileStorage` parked in `open` on a fifo with no reader, or any custom `Storage` that ignores its context, held `Close` — and with it `Recorder.Close` and the container's ordered teardown — for good, while the comment above the grace said that state had been repaired. After a second grace the worker is abandoned with whatever it still holds and `Close` returns an error naming how many entries stayed queued behind the save it could not end; those are not counted as dropped, since the worker still writes them if the delegate ever answers
- `audit.FileStorage.Save` refuses a context that is already done before it opens the file, the reading `BunStorage` gets from its driver. It ignored the context entirely, so after `AsyncStorage` cancelled its worker every entry still queued was written in turn instead of being dead-lettered as promised; an open or write already parked in the kernel is still not interrupted, since nothing in the process can do that
- encrypt: the bulk migrate binds an integer primary key's keyset cursor and update guard as the integer itself, read from the column's own reported type, instead of as the scanned text — MySQL compares an integer column against a string parameter as double-precision floats, so keys at and above 2^53 collapsed onto shared doubles: pages silently skipped the rows that rounded onto the cursor, none counted as skipped, and the `pk = ?` guard could match a neighbouring key in the same bucket
- `RouteDiagnostics` no longer pins bun's diagnostic channel to the FIRST logger for the life of the process. Bun's logger is one variable per process, so it is still set exactly once — but what is set is now a forwarder onto a destination every call replaces, and the destination is what decides where a record goes. A process that builds, closes and rebuilds its application — a test binary above all, but equally an application whose database registry is wired before its own logger exists — used to drop every later lifecycle's diagnostics into the first lifecycle's logger, closed by then or the emergency fallback nobody reads. A typed nil logger is now refused alongside a nil one, the reading the rest of this package already applies
- `ManagerRegistry.Close` waits for the opens that were still in flight when it published its refusal, on the ordinary door and on the migration door alike. Each of those ends its own freshly opened database against the closed flag, so nothing leaked before either — but Close returned while a dial was still in the air, and a process exiting on that answer left the connection outstanding, its server-side session to be reaped by a timeout rather than ended. The wait is unbounded by design; `NewManagerRegistryWithContext` is the door that shortens it. It also hands bun's diagnostic channel back last, while the logger it routed to is still alive
- `ReadWriteSplitter.Reader` refuses a wiring error instead of absorbing it into the fallback: a replica name the registry does not know, an empty name and a closed registry are permanent by nature, and folding them into the primary fallback routed every read to the primary forever with no signal that the replica configuration was dead. The fallback remains for what it exists for — a replica that failed to OPEN, a transient outage — and when the primary then fails too, the answer carries the primary failure as its cause and names the replica failure beside it, so the diagnosis stops pointing at the wrong database. The constructor refuses an empty replica name outright, and the round-robin counter moves to `atomic.Uint64`, which carries the alignment guarantee the plain field only had by field-order luck
- `audit.Registry` is safe for concurrent use: `Register` is public, returns the registry for chaining and stays reachable through `Recorder.Registry()` for the life of the process, while every recorded write reads the same map from a request goroutine — an unguarded late `Register` was a fatal concurrent map read and write no recovery could catch. The construction also copies the variadic global ignored fields, whose backing array used to stay the caller's to mutate under the readers
- `audit.Recorder.WithLogger` installs the logger under a lock, mirroring the guard `AsyncStorage` already had on exactly the same field, and refuses a typed-nil logger at the door rather than dereferencing it inside the very call that reports a failure
- the audit dead-letter records carry the failure's whole cause chain, its context and the target table: an `exception.Error` renders its message alone through `Error()`, so "could not write the audit entries" without the driver error and the table was the entire diagnostic an operator got for a trail that stopped filling — on the synchronous recorder and the async worker both
- `audit.Tracker` refuses a context carrying a caller-made `WithDatabase` binding: that binding means the caller already holds its own open transaction, and the Tracker — which owns a transaction of its own by contract — would open a SECOND one on the same pool, where the failure is not an error but a deadlock (the outer transaction holds the row the inner `SELECT ... FOR UPDATE` asks for, or N concurrent requests hold all N pool connections while each waits for one more). The two doors are documented alternatives; the refusal names the Recorder path a caller inside its own unit of work should take
- the `audit.Tracker` transaction MARGINS are wrapped with the entity and the operation: bun's `RunInTx` returns the `BeginTx` and `Commit` failures raw, so the commit deadlock and the connection lost at the last moment were the only failures that reached the caller with no entity and no operation on them — while the closure's own failures keep their identity untouched, so every `errors.Is` a caller performs keeps its answer
- the derived composite `entity_id` escapes `\` and `:` inside its parts: `("a:b","c")` and `("a","b:c")` both derived `a:b:c` and two different rows shared one history. Keys carrying neither character — the ordinary case — render exactly as before, so existing trails keep joining
- `audit.BunStorage.Save` enforces the table-name grammar itself, as an error on the request path: the Registry validates the names IT hands out, but `Save` is a public door whose table flows unquoted through `ModelTableExpr` as raw SQL, and a direct caller bypassed the Registry entirely. The silent `""`→default-table substitution goes with it — it hid the caller that forgot which table it was writing
- `audit.Registry.EnsureSchema` names the table it could not create, and issues its DDL in sorted order so the same failure names the same table on every run; both statements used to return the driver error bare, with the failing table known only to the map walk that chose it
- the `audit.AsyncStorage` worker runs each save under a recovery boundary: the worker is a bare goroutine, so a panicking delegate — a closed pool, a custom `Storage`'s defect — was a process crash raised from the audit trail, the one component whose failure the design explicitly demotes to a dead-letter. The panic is recorded like any failed save and the worker moves to the next entry
- `audit.AsyncStorage.Close` is bounded: past a five-second drain grace the worker's context is cancelled, the in-flight save aborts and the remaining entries are dead-lettered, with the forced form reported as an error naming the grace. The unbounded join used to let one full queue over a dead database hold the container's whole ordered teardown — the entire process refusing to exit; losing those entries to a backend that stopped answering is the trade this storage already made when it chose not to block the request path
- `audit.AsyncStorage.Save` honours a context carrying a database binding by writing through the delegate synchronously: queued, the entry was written by the worker outside and possibly AFTER the caller's transaction, so a rollback left a row in the trail for a change that never happened — the ghost the Tracker's atomicity promise exists to rule out. The queue keeps serving the unbound path, which is the one with a request latency to protect
- the audit auto-redaction recognises the compartment-bound generic column types: `EncryptedStringFor[R]` and `EncryptedDeterministicStringFor[R]` instantiate a distinct `reflect.Type` per marker, so the identity comparison matched the two default-cipher types and left every compartment column's plaintext live in the exported change-set — the type walk now answers the same question as the value walk for a struct whose only sensitive member is an encrypted column, and both go through the `EncryptedColumn` marker interface
- `audit.WithDatabase` refuses a nil handle, typed or bare: bound, it would either be ignored in silence — losing the atomicity the caller asked for — or dereferenced inside the caller's own transaction
- `encrypt` seal validates the key id against the wire-format grammar: the id is written into the stored value in front of a `:` separator, `StaticKeyProvider` enforces the grammar at construction, but `KeyProvider` is a public interface and a custom provider's empty or colon-carrying id produced a stored value `decodeEncrypted` could never split back apart — the write succeeded and the loss surfaced only at the next read, permanently
- `encrypt` decodes the stored base64 strictly: the lenient decoder mapped several spellings onto the same bytes, so an altered last character still authenticated while `CiphertextCandidates` only ever emits the canonical spelling — a deterministic equality lookup missed a row whose plaintext it held. Everything seal writes is canonical, so strictness refuses only what this cipher never produced
- `encrypt` floors a stored payload at nonce PLUS authentication tag: a seal of even the empty string is never shorter, so a 12-to-27-byte payload is structural damage — it used to pass the nonce-only floor and fail inside `gcm.Open` as "could not decrypt value", blaming an authentication failure on a key
- `encrypt.UseCipher` and `UseCipherNamed` refuse a TYPED-nil cipher: the bare nil stays the documented deinstall door, but a typed nil is a failed resolution installed anyway, and stored it was handed out by the registry with a nil error and dereferenced inside `database/sql` at the first column write
- the compartment reference resolution refuses a pointer-form marker: `EncryptedStringFor[*CrmCipher]` compiles whenever the value form does, and its zero value is a nil pointer whose `CipherName()` dereferenced nil from inside `database/sql`; it answers as an error naming the marker instead
- the migrator's column-width check reads the TEXT family in BYTES: `CHARACTER_MAXIMUM_LENGTH` reports the worst-case character count under the column's charset — 16383 for a TEXT under utf8mb4, a quarter of the 65535 bytes it actually holds — so the pure-ASCII ciphertext was refused for migrations that fit with room to spare, under a diagnostic naming a width nobody configured
- the migrator refuses a NULL pagination-cursor value the moment it shows: rendered as `""`, the next page's `pk > ''` coerces to `pk > 0` on an integer column — exactly the first-page hazard the keyset deliberately avoids, one page later — so a nullable or wrong `--primary-key` column stops the run instead of silently skipping rows
- an interrupted bulk migration names itself: a SIGTERM mid-run used to surface as "migrate select failed", indistinguishable from a missing column, so a deployment gated on the diagnostic could not tell "we stopped it" from "it is broken". Both remain errors — the column is partially migrated either way — but the interruption carries how far the run got
- `melody:encrypt:database` refuses a negative `--batch` by name — it used to silently become the default of 500, so the operator who believed they had throttled the run had not — and a failed run's error carries the rows already converted, the one number that says what a re-run costs and whether the column's mixed state is explainable
- the encrypt module refuses a kernel answering no service container at registration: the nil resolver used to be captured silently into the factory closure and explode at the first command run, far from the wiring that produced it

- `ManagerRegistry.Close` publishes the closed flag under the registry lock and tears the pools down outside it. A pool close travels the wire — a `COM_QUIT` to a peer that may be partitioned, and the migration connection deliberately lifts its write deadlines — so holding the lock for the whole teardown parked every other caller on it for as long as the driver waited, including the ones that flag exists to refuse at once: a graceful shutdown against a black peer drained with goroutines wedged in the registry instead of each receiving `ErrManagerRegistryClosed`. The two maps are snapshotted rather than emptied, so the entry refusal keeps reading the flag and a manager already handed out is unaffected. **Behavioural change** for a caller that relied on `Manager` blocking until the teardown had finished — see the framework's `UPGRADE.md`
- `Manager` refuses everything after `Close` instead of only the names it had not opened yet. `Close` ends every pool it memoized without emptying the map, so a name already opened was answered with the manager over the now-dead pool and a nil error, while the same call for an unopened name was refused only where the publish step noticed the flag — one registry answering the same question two ways, with the answer that looked like success failing at the first query. The refusal also spares the dial: an unopened name used to be dialed in full, retry backoffs included, before the publish step refused it. **Behavioural**: `Manager`, `DefaultManager`, `Database` and their `Must` forms now refuse after `Close`
- the three construction refusals name the definition they are about. `ErrProviderDefinitionNameIsRequired`, `ErrProviderIsRequired` and `ErrProviderDefinitionNameMustBeUnique` came back as bare sentinels, so a configuration carrying three definitions answered "provider is required" without saying which of the three was broken, and refused a duplicate without saying its own name. The record now carries the definition's position in the argument list and its name; each sentinel stays the cause, so every `errors.Is` keeps its answer
- a definition name the registry does not know is refused with the name that was asked for and the names that exist, on both doors — `Manager` and `MigrationDatabase` — the way the framework's own container names an unregistered service id. `db:migrate --manager=repots` printed "provider definition not found" and exited non-zero, with both halves of the answer in the registry's hand and neither in the record. `ErrProviderDefinitionNotFound` stays the cause, so every `errors.Is` keeps its answer, and the registered names are sorted so one misspelling always prints one list
- the recovery boundary of a lazy open names what actually unwound instead of blaming the provider for both. An unwind that reaches it after the provider has already returned is the registry's own publish, which calls into the freshly opened database, and sending whoever reads the record to the provider sends them to code that did nothing; an unwind carrying no value at all is a goroutine exit rather than a panic, which is what a `t.Fatalf` inside a provider produces and what left the coalesced waiters holding `panic: <nil>` over something that never panicked. The refusal now names the stage and the outcome, and the `panic` key is present only where a panic value exists
- the error handed to callers coalesced onto a panicked open carries the panic value as its CAUSE and the stack of the goroutine that raised it, not only a stringified copy in its context. The re-raised panic reaches a boundary that records both, so the waiters — who never see that panic — were the only callers handed a flattened message, for the same failure, decided by which goroutine they happened to be on. A typed-nil panic value answers no cause, since its `Error()` would dereference a nil receiver at the first render of the very error the boundary exists to hand on
- a provider answering neither a database nor an error is refused with `ErrProviderReturnedNilDatabase` instead of being memoized as a manager wrapping nil, which handed callers a nil `*bun.DB` with no error and panicked at the first query; the refusal is not memoized, so a repaired provider is retried. Both open paths — `Manager` and `MigrationDatabase` — refuse it
- a database handed over beside a non-nil error is closed instead of leaked: the `Provider` contract does not promise a nil database with the error, and the registry was the last holder of that pool. Both open paths close it
- `NewManagerRegistry` refuses a typed-nil logger or provider. A nil concrete pointer boxed in the interface passed the plain nil comparison, so the boot-time refusal degraded into a panic at the first resolution, far from the wiring mistake that produced it
- `Close` names every database that failed to close: with several failures, only the first was returned and the rest left no trace anywhere. A lone failure keeps its own error untouched
- `Close` walks the managers and the migration databases in sorted name order, so the carried cause and the failed-name list are the same for the same failing teardown on every run: the map walk let two identical failures report different causes and different orders, where the rueidis batch reporting already sorts for the same reason
- the registry's bound context reaches the MIGRATION open. `NewManagerRegistryWithContext` promises that a provider implementing `ContextOpener` has its lazy opens run under it, and `MigrationDatabase` opened through `OpenForMigration`, which carries no context at all — so a `db:migrate` that received SIGTERM against a down database slept through the whole retry budget instead of refusing at the first cancellable step, which is the exact window a supervisor's signal lands in. A provider carrying only `MigrationProvider` is unaffected: the new capability is optional
- the `Provider` contract documents the ownership transfer its registry already enforces: `Open` answers a fresh pool that the registry closes whenever it decides not to keep it — handed back beside an error, losing a duplicate migration open, or landing after `Close` — so an implementation handing out a shared or memoized `*bun.DB` is outside the contract
- the registry's own suite orders its interleavings by observing the registry rather than by sleeping. Five tests — the three panic-coalescing ones and the two close-during-open ones — waited a fixed hundred milliseconds for a state they could read, and a lost interleaving did not merely flake: the coalescing caller became a fresh opener, the provider panicked again on a goroutine with no recover above it, and the whole test binary died where one assertion should have failed. Each now takes the in-flight entry the open registers before it dials, or waits for the closed flag to be answered by a door, so the wait ends exactly when the condition holds
- the coalescing of concurrent first dials is pinned by two registry tests: the in-flight entry is registered under its name before the provider is dialed, and a caller that finds an in-flight open waits on it and answers with the published manager instead of dialing a second pool — the waiter is constructed by hand, so no scheduling window decides what the tests observe
- encrypt: the capacity check covers a rotation to a longer key id, which grows every stored value and could truncate a column that fitted before. The required width is measured from the longest stored value with its own key id removed, because a column mid-rotation holds several of them and a flat difference against the provider's current key reads as zero exactly when the rotation has already begun. Plaintext left in the column is measured under the key the rotation will seal it with
- encrypt: a stored value carrying the encryption marker whose payload no longer decodes is reported as an error instead of being returned verbatim. The marker is the framework's own, so its presence means the value was encrypted here and a failure to decode means damage — a column truncated by a permissive `sql_mode` read back as garbage with no error at all. Genuine plaintext, which carries no marker, still passes through so an incremental migration works as before
- audit: a cyclic field type no longer exhausts the stack or spins forever. The walk that looks for a redact tag consulted its visited set only when it reached a struct, so a type reaching itself through a map — `type Attributes map[string]Attributes` — recursed until the stack was gone, and a type reaching itself through a slice or a pointer spun a processor at full load. Since a stack overflow is a fatal error no recovery layer can catch, the first audited write of such an entity ended the process and every restart ended it again. A type met a second time is answered from the frame still exploring it, so a redact tag remains found by whichever path reaches it
- audit: an entity embedding a pointer to itself is recorded rather than exhausting the stack. Go permits `type Node struct { *Node }`, and the change collector followed it with no cycle guard; the before and after graphs are now tracked by pointer identity, kept apart from each other so a pointer both sides share — the ordinary shape of an untouched embed — is not mistaken for a loop, and a finite embed chain is still walked in full
- encrypt: the pre-image guard compares the stored bytes rather than the column's collation, so a row an application rewrote between the run's read and its write is skipped and reported instead of being overwritten. Under MySQL 8's default collation a concurrent case normalisation still matched the guard, so the run reported success while destroying the application's write and storing a ciphertext that decrypts to the stale value; a trailing-space change slipped through the same way under any PAD SPACE collation
- encrypt: `melody:encrypt:database` refuses to run when a target column is too narrow for the ciphertext it would have to hold, naming the column and the width it needs. Sealing expands a value by roughly a third plus a fixed header, so a `VARCHAR(255)` stops fitting at 153 bytes of plaintext; with a non-strict `sql_mode` the row was silently truncated and counted as migrated, and the truncated value does not even fail authentication on the way back — it is returned verbatim with no error. The required width is measured by sealing a probe with the live cipher, so it cannot drift from the encryption itself
- encrypt: every `NewFakeCipher` carries its own identity. `fakeCipher` was a zero-size struct, so all of them shared one address and compared equal as interface values — a test asserting that the named and the default compartment resolve to different ciphers could not fail, and a registry cross-wiring the two lookups kept it green
- encrypt: `melody:encrypt:database --mode=encrypt --deterministic` converts a column that was already bulk-encrypted with random nonces into its deterministic form, keeping the key each value already carries. Every such value previously authenticated under a live key and was passed through untouched: the command reported success and rows processed while converting nothing, the column stayed randomized, and every `CiphertextCandidates` equality lookup on it returned zero rows — a silent login or lookup failure. **Behavioural change**: a deterministic encrypt run over an already-encrypted column now rewrites those rows. It remains idempotent, and it never rotates keys, so `--mode=reencrypt --target-key=...` is still the only way to change a key
- audit: an empty change-set is always serialised as `[]`. Only the "no models at all" case previously produced an empty array; an idempotent update whose before and after are identical — an idempotent `PUT` or a client retry — and any non-struct model left the change-set nil, so the `changes` column stored the json literal `null`. A trail consumer running `jsonb_array_length(changes::jsonb)` errored or read `1` instead of `0`, and the two shapes were indistinguishable from a genuinely absent change-set

- `audit`: an audited delete that captures no before-image records an empty change set rather than the json literal `null`, so a reader of the trail parses one shape
- `encrypt`: the bulk migration keeps a count and a bounded sample of the rows it skipped instead of every skipped primary key, so a large table under a concurrent writer no longer accumulates the whole set in memory on the way to reporting the error
- the manager registry no longer wedges permanently when opening a database panics while the registry is being closed. The section that publishes the opened manager released its lock without a defer, so a panic from the database's own `Close` unwound with the lock held and the recovery path then blocked on that same lock — after which every later call to the registry blocked forever, silently. A provider returning a nil database was enough to trigger it
- `audit/track.go`, `audit/config.go` — `Tracker.Delete` no longer records field values it never read. The caller typically holds only the primary key, so the remaining fields of the passed-in model are zero values, and recording them asserted them as the deleted row's contents — permanently, for a row that no longer exists; a caller could just as easily write a false before-image by hand. The trail now carries what the delete actually knows: the identifier, the actor and the time. An entity whose deleted contents must be recoverable opts in per entity with `EntityOptions.CaptureDeleteBeforeImage`, which loads and locks the row with `SELECT ... WHERE pk FOR UPDATE` before removing it; it is off by default, so auditing charges the working database no extra read on the normal path, and only an opted-in entity pays the select, the row lock and an error when the row it must capture is already gone. A delete that matched no row is not recorded at all, instead of writing a deletion that
  never happened
- encrypt: the bulk column migration reports a run as incomplete instead of successful when a guarded update matched no row. Each update is guarded on the value read for that row, so a row the application changed between the select and the update matches nothing and keeps its plaintext; the affected count was discarded and the row was still counted as processed, so the command logged success and exited zero over values it had never migrated — and under `--mode reencrypt` that left a row on a key about to be retired. The run now names how many rows it left untouched and exits non-zero, and a re-run picks them up under their new values
- encrypt: the readme states as its own caveat that a sealed value must never be passed as a `string` argument to a raw statement. The marker's `\0` glue bytes are what identifies it, and bun's formatter drops embedded NUL bytes when it inlines a `string` into the SQL text, so `set email = ?` with a `string(sealed)` stores a value the marker no longer matches and the next read takes the unmarked pass-through, handing the application the base64 body as if it were plaintext. Through the model types this cannot happen — their `Value()` returns `[]byte` — and the rule was previously stated only as the reason `CiphertextCandidates` returns `[][]byte`

## [v3.2.0] - 2026-07-11 - Named Cipher Compartments and Manager Registry Hardening

### Added

- `encrypt/cipher_registry.go`, `encrypt/encrypted_string_for.go`, `encrypt/deterministic_for.go` — named cipher compartments for multi-context binaries. `UseCipher` was process-global with one current write key, so two DB contexts with separate key sets could not keep separate current keys — consolidating apps meant merging key maps and losing a key compartment that existed when the binaries were separate. Now each compartment installs its own cipher with `UseCipherNamed(name, cipher)` and binds columns through the type system: a zero-size marker implementing `CipherRef` (`CipherName() string`) parameterizes the new generic column types `EncryptedStringFor[R]` / `EncryptedDeterministicStringFor[R]` — the only channel available, since `database/sql` gives `Value()`/`Scan()` no context. Compartments are truly isolated (the "crm" cipher can never decrypt a "billing" ciphertext — unlike per-column key selection over a merged provider, where either context can read the other's rows), key
  rotation inside a compartment keeps working through the key id embedded in the ciphertext, and the generic types replicate the full redaction surface (`String`/`LogValue`/`MarshalJSON`). `UseCipher` and the existing column types are unchanged — the default cipher is now simply the registry's reserved unnamed entry. Per-`Manager` cipher binding was rejected: a `driver.Valuer` has no manager context, and bun query hooks would miss raw SQL paths.
- `encrypt/module.go`, `encrypt/encrypt_database_command.go` — the bulk command module composes with compartments: `ModuleConfig.Contexts []CommandContextConfig{Name, Database, Cipher}` registers one `melody:encrypt:database:<name>` command per compartment (via the new `NewEncryptDatabaseCommandWithName`), while the legacy `{Database, Cipher}` fields keep the unsuffixed command.

### Fixed

- `manager_registry.go` — a panic inside `Provider.Open` no longer wedges every later caller. `Manager` opens outside the registry lock and coalesces concurrent callers of the same name onto one open, so when a mis-parameterised provider panicked (the pgsql/mysql providers resolve parameters with `MustGet`) the deletion of the in-flight entry and the close of its done channel were skipped, and a recovered panic left every subsequent `Manager(name)` blocked forever on the never-closed channel. The open is now wrapped so the slot is always cleared and waiters are released with an error, while the panic still propagates to the direct caller.
- `manager_registry.go` — a database opened while `Close` is running is no longer leaked. `Close` drains the manager map without an open still in flight, so an open completing afterwards memoised its `*bun.DB` into a registry nobody would drain again; `Manager` now closes the freshly opened database and returns `ErrManagerRegistryClosed` when it finds the registry closed on completion.
- `encrypt/key_provider.go` — `StaticKeyProvider` redacts its keys under `fmt`. The `%#v` and `%v` verbs walk unexported fields, so a provider that reached a debug log — or an error context formatted later — printed every AES master key as raw bytes. This is the redaction class the encrypted column types already close, applied to the material those columns are protected with.
- `encrypt/encrypted_string.go`, `encrypt/deterministic.go`, `encrypt/encrypted_string_for.go`, `encrypt/deterministic_for.go` — the encrypted column types now redact under the `%#v` verb too. `fmt` reaches for `GoStringer` there and, finding none, printed the underlying string literal, so a struct dumped with `%#v` into a log line or a test failure carried the plaintext — while `%v`, `String()`, `LogValue()` and `MarshalJSON()` all redacted correctly.
- `encrypt/encrypted_string_for.go` — a `CipherRef` whose `CipherName()` is empty is now rejected instead of resolving the default cipher. The empty name is the default cipher's reserved registry entry, so a marker that returned it silently handed a compartment-bound column the default key — exactly the cross-compartment read the marker type exists to prevent.
- `encrypt/key_provider.go` — `StaticKeyProvider` implements `fmt.Formatter`, so the numeric verbs (`%d`, `%o`, `%b`, `%c`, `%U`) can no longer bypass its redaction and print the raw AES-256 master key bytes. The `%#v`/`%v` redaction added earlier left these verbs, which walk the underlying byte slice directly, as an open channel.
- `encrypt/cipher.go` — a client-supplied marker-shaped string naming an unknown key id is sealed under the current key by `Encrypt` rather than stored verbatim, so a row can no longer be poisoned into a permanent key-not-found on a later `Scan` or re-encrypt/decrypt run. Pass-through is granted only to a value that decrypts under a key currently in the key set (a retired key stays in the set until re-encryption completes).
- `manager_registry.go` — `ManagerRegistry` no longer holds its internal lock across `Provider.Open`. A slow or unreachable database otherwise serialized `Manager`/`Database`/`Close` for every other database and stalled shutdown; concurrent openers of the same manager now coalesce onto one open, and a failed open is not cached.

### Added

- `v3/encrypt/` — transparent column encryption at rest with AES-256-GCM, designed as a drop-in over plaintext tables. `Cipher` is an interface (`NewCipher(KeyProvider)`) with a process-wide `UseCipher`; encrypted values carry a marker `<ENC>\0gcm1\0<keyId>:<base64(nonce||ciphertext)>` so reads can tell ciphertext from plaintext: `Decrypt` passes an unmarked legacy value through unchanged (existing rows read correctly and are encrypted on the next write) and `Encrypt` is idempotent on an already-marked value (double-encryption guard). `EncryptedString` (a `driver.Valuer`/`sql.Scanner`) **fails closed** — `Value`/`Scan` error if no cipher is configured rather than silently persisting plaintext — and masks its plaintext in `fmt`/`slog`/error output (`String`/`LogValue` return `<redacted>`). As `[][]byte` each candidate is emitted as an `X'…'` binary literal, so the lookup matches the stored value byte-for-byte. The README lookup example is updated accordingly.

- `v3/audit/` — `AsyncStorage.WithLogger` no longer races the background drain goroutine. The goroutine starts in the constructor, so attaching a logger via the builder while a failing save called `deadLetter` was an unsynchronised read/write of the `logger` field; it is now guarded by a dedicated mutex (separate from the queue mutex to avoid lock nesting in the `Save` → `deadLetter` path).
- `v3/audit/` — a `audit:"redact"`-tagged member reached through an `interface{}`/`any` column is now redacted too. `ChangeSet` walks a field's **static** type tree to find a nested `redact` tag, but an interface field hides its concrete type, so a redact-tagged struct assigned into an `any` column was serialized whole and leaked its plaintext into the `changes` column (encrypted types stay safe via their `MarshalJSON`, but a plain `redact` tag has no serialization guard). The matcher now also inspects the **dynamic** type of the captured value, complementing the static walk that already covers concretely-typed composite fields.
- `v3/audit/` — redaction detection now also inspects **map keys**, not only map values. A `map[encrypt.EncryptedString]V` (or a map keyed by any redact-tagged type) leaked its key plaintext into the `changes` column because `encoding/json` serializes a string-kind map key directly from its underlying value, bypassing the key type's `MarshalJSON`. Both the static type walk and the dynamic value walk now follow the map key as well as the value, so the whole containing field is redacted when a sensitive type or `redact` tag appears in either position.
- `v3/audit/` — the dynamic-type redaction above now descends through **nested** interface values, not just an interface used as the column itself. The previous check ran a static type walk on `reflect.TypeOf(value)`, which still could not see a `redact`-tagged struct carried by an `any` field one level deeper (`struct{ Inner any }`) or held as an interface value inside a map/slice (`map[string]any`), so such plaintext still leaked into the `changes` column. Redaction detection now walks the captured **value**, following interface, pointer, slice/array element, and map value boundaries to their concrete types, so a `redact` tag (or an encrypted column type) is honored at any depth regardless of interface indirection.
- `v3/audit/` — the value walk above no longer skips a `redact`-tagged (or encrypted) value reached through a **second sibling of the same struct type** whose sensitive content is only reachable via an `interface{}`/`any` field. The walk deduplicated visited struct **types** to break cycles, so once one instance of a type surfaced no redact marker (its interface field happened to hold a non-sensitive value) a later same-typed sibling — whose interface field did hold a redact-tagged struct — was short-circuited without inspecting its fields, leaking the plaintext into the `changes` column. Cycle detection now tracks visited **pointers** rather than types, so each distinct value of a repeated type is inspected on its own while genuine pointer cycles still terminate.
- `v3/audit/` — the redact-tag value scan no longer overflows the stack on a self-referential **slice** reached through an interface element (`d := []any{nil}; d[0] = d`). The map case recorded its header in the cycle set but the slice case did not — and a slice can self-reference through an `any` element with no pointer node for the deref loop to catch — so such a slice recursed forever and crashed the process. The `reflect.Slice` case now records the slice header before walking its elements, mirroring the map guard (`reflect.Array`, which cannot self-reference, keeps the plain walk).
- `v3/audit/` — a bun many-to-many relation field (`bun:"m2m:join_table,…"`) is now skipped in the diff like other relations. `auditFieldName` skipped only `rel:`-prefixed tags, so a loaded `m2m:` relation slice was treated as a column and serialized into the `changes` column — audit-table bloat plus another entity's rows recorded under this entity's audit row, bypassing its per-entity `IgnoredFields`. The `m2m:` prefix is now skipped too.
- `v3/audit/` — `Tracker.Update` now reads the before-image with `SELECT … FOR UPDATE` (it already runs inside the audited transaction). The plain select read a snapshot under MySQL's default isolation, so two concurrent audited updates on the same row could both record `before = A` (`A→B` and `A→C`) and the audit chain no longer reconstructed the data history; the row lock serializes audited writers per row.
- `v3/encrypt/` — `Migrator` bulk encryption no longer silently reverts a concurrent application write. Each row's `UPDATE … SET col = encrypt(old)` was guarded only by `WHERE pk = ?`, so an application write that landed between the migrator's read and write was overwritten with the stale pre-image — a lost update on a feature designed for online adoption. The update is now additionally guarded on the value read for each column (`AND col = ?`), so a row that changed under the migrator matches zero rows and is re-encrypted on the next run instead of being clobbered.
- `v3/encrypt/` — `Migrator` bulk encryption no longer skips rows whose primary key is zero or negative. The keyset pager seeded the cursor with the empty string and always filtered `WHERE pk > ?`, which MySQL coerces to `pk > 0` on an integer key — so `id <= 0` rows (and a string key equal to `''`) were never visited while the command reported success. The first page is now unfiltered and only subsequent pages apply the keyset predicate.
