## [v3.2.1] - 2026-10-21 - Failed Send Ends the Batch

### Fixed

- **Behavioural change** — `relay.go`: a failed send ends the batch. The failed row alone is charged an attempt, and the rows the batch had not reached are handed back pending with their attempts unchanged, available again when the failed row is tried again, their `last_error` naming the row whose failed send held them. Before, the batch went on and charged every claimed row an attempt on every pass, so a broker outage of about 66 minutes at the default settings dead-lettered every good message the relay claimed; a claim takes the lowest id first, so an outage now charges the first row of each claimed batch alone, pass after pass, and dead-letters one row of that batch per ~66 minutes, every poll that finds rows enqueued during the outage claiming a batch of its own. A contained send panic ends the batch the same way. A hold write that fails, or a cancellation of the run, ends the hold, the rows not handed back re-surfacing after `VisibilityTimeout`. Once the broker is back, the held
  rows
  wait out the failed row's current backoff, at most `MaxBackoff`, and a message the broker refuses holds the rows behind it for its own backoff each time it is due. When the failed send dead-letters its row, the held rows still wait the backoff that row would have had, `MaxBackoff` at the default settings.
- `relay.go` — a failed send writes one `outbox message send failed` ERROR record with the row's id, its type, the attempt it was charged, `MaxAttempts`, when it is tried again or that it was dead-lettered, and the transport's cause, written once the row's reschedule or dead-letter write succeeded, where a rescheduled row left no trace in the process log, `RunOnce` answering no error for it and the cause reaching only `last_error`; the batch ends at the failed send, so a pass writes at most one such record, and a contained send panic keeps its own `outbox delivery panicked` record instead

## [v3.2.0] - 2026-10-19 - Fenced Lease Refresh, Per-Row Contained Panics and Bounded Claim Limits

### Changed

- `go.mod` — requires `github.com/precision-soft/melody/v3` at `v3.14.0`, raised from `v3.11.0`, the lowest framework version this release builds against; a module that requires this release is pulled up to those versions with it
- **Behavioural change** — `relay_command.go`: `--limit` parses in base ten through `output.DecimalIntegerConfig`, `--limit=010` reading ten and `--limit=08` eight, where the engine's inferred base read eight and refused; a base prefix is refused as syntax.
- **Behavioural change** — `relay.go`: a lease refresh that fails mid-batch no longer ends the run at that row: the claimed rows are fenced by their claim token and invisible to whoever holds the lease now, so `RunOnce` drains the batch to its end under its claim tokens, does not retry the refresh, and reports the failure once the batch is done, the command's loop logging it and backing off, where the run returned at the failed refresh and left every unreached row claimed for the whole `VisibilityTimeout`, the lease being an optimisation and the rows never at risk of a double publish
- `relay.go`: a panic raised by the codec's `Decode` or the transport's `Send` is contained per row and charged to that row as the failure the collaborator would have returned, a decode panic dead-lettering the row, a send panic taking the retry path, the panic in `last_error` under a `panic: ` prefix and one `outbox delivery panicked` record naming the row and the phase, the batch going on, where a panicking row killed the relay process at every claim until the crash-poison cap dead-lettered it hours later; a panic raised by the repository is still not contained, a resolution written after it going to the same repository

### Fixed

- documentation: the entry for a codec or transport panic no longer carries the behavioural-change marker, a crash not being a behaviour an application relied on; and the README says that `--idle-backoff` defaults to the poll interval
- relay: the stored `last_error` cap cuts on a rune boundary, where a byte-offset cut through a multi-byte rune left an invalid string a strict utf8mb4 column refuses, failing the resolution write and re-surfacing the row every visibility timeout; and the distributed lease is released on a context detached from the run, bounded by five seconds, a release failure logged, where the release rode the run context, an interrupt cancelled it before the backend saw the delete, and the lease survived for the whole `LockTtl` (thirty seconds by default) with every other replica's `RunOnce` answering `0, nil`, stalling delivery on every graceful restart
- `relay.go` — the record of a contained panic carries `panicStack`, out of `last_error`; the resolution writes, sent, rescheduled and dead, run on a context the run's cancellation does not reach, bounded by five seconds, where a SIGTERM between a send and its mark failed the mark and the published row came back and published again; one WARNING per dead-lettered row names it, its type, its attempts and the stored error, where `last_error` was its only trace; a dead-lettered or rescheduled row's `last_error` records the failure's CAUSE CHAIN, capped so the narrowest default column the schema produces accepts the write, where it read `amqp publish failed` with no broker verdict; a failed resolution write reports the delivery failure it was recording instead of replacing it, where a hiccup in `MarkDead`/`Reschedule` lost the decode/send cause from the log and the row; and the lease-refresh cadence is anchored at `Acquire`, before the claim, where a claim blocked on a contended database
  consumed lease lifetime the post-claim anchor never counted and the first refresh could land after the lease had lapsed
- `store.go`, `relay.go` — `Store.ClaimDueMessages` refuses a non-positive limit by name, with the limit in the error's context, and cuts a limit above the relay's own cap (100000) to it, where bun writes no `LIMIT` clause for a non-positive value and narrows to int32 first, so zero, a negative and a value past the int32 range that narrowed to zero or below claimed the whole table in one transaction; and `BatchSize` is clamped from above as well as below, the store capping its allocation hint independently, where a configuration with too many zeroes asked the runtime for terabytes of slice capacity and panicked the relay before any query ran, past the command's error-driven backoff
- `relay_command.go` — a genuine batch failure that coincides with the parent context's cancellation or deadline is returned instead of swallowed, only an error wrapping `context.Canceled`/`DeadlineExceeded` exiting clean, where a supervisor read a failed drain as exit 0; and `resolveRelay` reports a nil relay yield as an error instead of dereferencing it, mirroring the lazy repository's guard, latent defense against a userland decorating resolver

## [v3.1.0] - 2026-07-17 - Store and Relay Factories with Lazy Resolution

### Added

- `module.go`, `relay_command.go` — `ModuleConfig` accepts a `StoreFactory`/`RelayFactory func(resolver) (*Store/*Relay, error)` as an alternative to a prebuilt `Store`/`Relay`. The factories are registered as the service providers (resolved lazily) and `NewRelayCommandFromResolver` resolves the relay inside the run loop — a resolution failure follows the same doubling error backoff as a failed batch and the relay proceeds once a later resolution succeeds — so an app whose `*bun.DB` is resolved from a registry per context — not available before `Boot()` — can register the module and use the built-in `melody:outbox:relay` command without a prebuilt object at composition-root time. Setting both a prebuilt object and its factory (`Store`+`StoreFactory` or `Relay`+`RelayFactory`) is an ambiguous configuration and panics at `RegisterServices`, before any service is registered. A database or store opened inside a factory is not closed by the container at shutdown — factories should resolve
  container-owned services, or register the closeable resource as its own service.
- `lazy.go` — `NewLazyRepository(resolver)` returns a `Repository` that defers resolving the registered `service.outbox.store` until its first call, so a component assembled during boot can hold the outbox repository before the container is safe to resolve. A store that cannot be resolved — or resolves to nil — surfaces as the call's error and is retried on the next call, never as a panic: the relay drives this `Repository` from its error-driven backoff-and-retry loop, and a panic would take the whole relay process down on a transient store outage. A nil resolver panics at construction, like the sibling constructors. The concrete `*Store` (with `Enqueue`/`EnsureSchema`) is reachable the same way through the generic `container.Lazy[*Store]`.

## [v3.0.0] - 2026-07-06 - Initial Release — Transactional Outbox with Relay Module and Command

### Added

- `module.go`, `service_resolver.go`, `relay_command.go` — the outbox now follows the integrations' composition convention: `NewModule(ModuleConfig{Store, Relay})` registers the store and relay under the canonical container names `service.outbox.store` / `service.outbox.relay` (helpers `StoreMustFromResolver`/`StoreMustFromContainer`, `RelayMustFromResolver`/`RelayMustFromContainer`) and exposes the new `melody:outbox:relay` CLI command, which owns the relay lifecycle every adopter previously had to hand-roll: it polls `RunOnce` on a `--interval` cadence (default 1s), sleeps `--idle-backoff` after an empty batch, stops after `--limit` batches (0 = until interrupted), backs off exponentially on consecutive batch failures (capped at one minute, so a repository outage does not tight-loop) and exits cleanly on SIGINT/SIGTERM (a signal landing mid-batch aborts the drain; the claimed rows re-surface after `VisibilityTimeout`). A `README.md` documents the pattern, and the module is listed in
  the integrations index.
- Initial transactional-outbox helper. `Store` (bun-backed) writes outbox rows: `Enqueue(ctx, executor, message)` takes a `bun.IDB`, so passing the caller's `bun.Tx` commits the outbox row atomically with the business write — the point of the pattern. A `Relay` (`NewRelay(RelayConfig{...})`) drains pending rows to any core `messagebus/contract.Transport` (e.g. the AMQP transport) with exponential backoff and a terminal dead-letter state: `RunOnce` publishes one batch of due messages, marking each sent, rescheduling a failed send with an incremented attempt count and capped backoff, and dead-lettering once `MaxAttempts` is reached or when a row cannot be decoded (poison). Every batch is claimed atomically — `ClaimDueMessages` selects due rows `FOR UPDATE SKIP LOCKED` inside a transaction and flips them to an in-flight state with `available_at` pushed out by a `VisibilityTimeout` — so two instances never grab and publish the same row even without a Locker, and a row an instance claimed
  but crashed before resolving re-surfaces once its visibility lapses (requires a backend supporting `SELECT … FOR UPDATE SKIP LOCKED`: PostgreSQL, or MySQL 8+). A separate `delivery_attempts` counter — charged per row when the relay actually attempts its delivery (`RecordDeliveryAttempt`, persisted before the decode/send that can crash), not for the whole batch at claim time, so a batch-mate the relay never reaches is never charged an attempt it never received and never falsely dead-lettered behind a crashing row — bounds the re-surfacing case: a row that keeps crashing or hanging the relay between the recorded attempt and resolve never advances its send-failure `attempts` and so would loop forever, but once its recorded delivery attempts exceed `MaxDeliveryAttempts` (default twice `MaxAttempts`, since normal retries re-claim too; a configured value that does not exceed `MaxAttempts` is raised to that default, since otherwise a normally-retrying row would be dead-lettered as poison
  after its first re-claim; the doubling is overflow-safe — a pathologically large `MaxAttempts` saturates the derived cap to `math.MaxInt` rather than wrapping it negative, which would otherwise dead-letter every message on its first delivery) it is dead-lettered as poison rather than re-surfacing indefinitely. The terminal writes (`MarkSent`/`Reschedule`/`MarkDead`) and the per-row delivery-attempt record are fenced by a per-claim token — a `claim_token` column rewritten on every claim — so a slow run whose claim already lapsed and was re-claimed by another instance cannot clobber the new owner: its guarded writes match no row (guarding on the in-flight status alone is insufficient, because a re-claim returns the row to the same in-flight state the stale run also holds, so it could otherwise revive a row already marked sent or dead-letter one mid-delivery). Each published message carries the outbox row id as a `messagebus.MessageIdStamp` (a stable `melody-outbox-<id>`), which the
  AMQP transport publishes as the message id, so a consumer can deduplicate the redelivery an at-least-once outbox can produce after a transport-success-then-crash. An optional core `lock/contract.Locker` (e.g. the Redis locker) additionally leases the relay so only one instance drains at a time; the lease is refreshed as the batch progresses (twice per `LockTtl`) and the run aborts if it can no longer be held, so a batch that outlives the ttl cannot be taken over and double-published mid-run. The exponential backoff is overflow-safe: a very large `MaxBackoff` and factor cannot wrap the duration negative and defeat the cap. Messages are stored and rebuilt through an application-supplied `MessageCodec`, and persistence sits behind a `Repository` interface that the `Store` implements, keeping the relay's retry/dead-letter logic unit-testable without a database. The reference design is Curatorium's `payment` outbox (15s base backoff, 12 attempts, Redis lease, dead-letter). Depends on the
  core `melody/v3` and `github.com/uptrace/bun`.
