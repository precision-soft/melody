# Changelog

All notable changes to `precision-soft/melody/integrations/rueidis/v3` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `WithLockerCallTimeout`, `LockerOption`, `NewLockerWithOptions`, `RegisterLockerServiceWithOptions` and `ModuleConfig.LockerOptions` bound one round trip of every door of a lock, default 1s. Measured on a live redis over a connection whose replies were gated: `Acquire`, `Release` and `Refresh` — each one Lua script, a write — on a context without deadline were ended by the client's own `ConnWriteTimeout` after 5.00s, and melody's http kernel hands a request no deadline, so a readiness handler taking the lock waited the whole ceiling on every attempt, and so did the framework's `RunExclusive`, which acquires on the caller's context. The locker now caps the runtime context with the timeout and keeps a caller deadline that is tighter; the registration door with options and the module field hand the option to the locker registered in the container, and `NewLocker` and `RegisterLockerService` keep their signatures and build the locker at the defaults. A non-positive value falls back to the default, the package's convention
- `WithNonceGuardCallTimeout`, `WithNonceGuardKeyPrefix`, `NonceGuardOption` and `NewNonceGuardWithOptions` give the nonce guard the options it had none of, the call timeout above all, default 1s. Measured over the same gated connection: the Lua record behind `Remember` was ended by the client's ceiling after 5.00s, while the read-only `EXISTS` behind a non-positive ttl — the existence check the contract asks for at the acceptance-window edge — had not returned after fifteen seconds, the client retrying a read-only command on a fresh connection for as long as a context without deadline allows. The guard now caps the request context with the timeout on both round trips and keeps a request deadline that is tighter; `NewNonceGuard` and `NewNonceGuardWithPrefix` keep their signatures and build the same guard
- `WithTokenStoreCallTimeout` bounds one round trip of every token store door, default 1s. Measured on a live redis over a connection whose replies were gated: a write — the `EVALSHA` behind `Put`, `Delete`, `RevokeBefore` and `Lookup` — on a context without deadline was ended by the client's own `ConnWriteTimeout` after 5.00s, while a read-only command — the `SSCAN` behind `DeleteByUser`, the `SCAN` behind `PurgeExpired`, the `HMGET` behind `RevocationEpoch` — was retried by the client on a fresh connection for as long as the context allowed, and a context without deadline, which is what melody's http kernel hands a request, allows forever. The context-less half of the contract now runs each round trip under the timeout, the runtime half caps the request context with it and keeps a request deadline that is tighter, and the bound is per round trip rather than per operation, so a walk over a large user's index gets one budget per batch. A non-positive value falls back to the default, the package's convention
- `cache.RegisterBackendServiceWithOptions` and `cache.ModuleConfig.BackendOptions` hand `BackendOption`s to the backend registered in the container — `WithCommandTimeout` above all, which nothing in the container wiring could pass before: the registered backend ran its context-less doors unbounded, and measured over the same gated connection a `Get` on it did not return within thirty seconds, the client retrying the read for as long as a context without deadline allows. `RegisterBackendService` is unchanged and still registers the backend unbounded, the subpackage's documented default; the example application registers through the module with a one-second timeout
- `ServiceConnection` and `RegisterConnectionService`: the `Connection` that owns the client finally has a registration door, and every client-backed provider in this package — the client itself, the locker, the token store and the cache backend — resolves it when it is registered, recording the dependency edge that orders the teardown: whichever run resolves one of them thereby guarantees the connection closes after it, exactly the guarantee shape the messagebus transports carry. A run that resolves none leaves the connection unresolved and therefore unclosed — the container closes only what was resolved at least once — and that boundary is documented where the door is
- `ModuleConfig.Connection`: handing the module the owning `Connection` beside (or instead of) the raw client registers the owner service, and a nil `Client` is read off the connection, so the composition root does not have to carry both. Until now the module registered the raw client alone, whose `Close` returns nothing — the client could never join the ordered teardown at all, and it lived exactly as long as the process
- `NewConnection` wraps a client in the closer shape the container's teardown recognizes. `rueidis.Client.Close` returns nothing, so the raw client could never join the ordered shutdown — the container closes what answers `Close() error` and nothing else — and every value in this package that could close a client it merely borrows deliberately declines to, so nothing closed it at all. Register the `Connection` as the service that owns the client and resolve the client through it; `Close` closes the wrapped client exactly once and answers nil afterwards
- `cache.WithCommandTimeout` bounds every backend operation dispatched without a caller context. The ctx-less half of `cache/contract.Backend` carries no deadline of its own, so a request-path read against a store that accepts connections but stops answering hung the handler; a non-positive value reads as unbounded, which is the behaviour of a backend built without the option. The two frozen majors expose the same capability through second constructors (`NewBackendWithCommandTimeout`, `NewBackendServiceWithCommandTimeout`); this major already configures its backend through options, so it arrives as one
- the provider's refusals carry the deadlines that governed the attempt — the connect timeout, and the dial timeout reported as the value that actually governed rather than the one configured. The custom dialer is installed only for a positive `DialTimeout`, so a zero or negative one ran under the library's own five seconds while a record built from the configuration would have said `0s`, which an operator reads as no dial bound at all. The credential is never part of the record

- `WithTokenStoreMaximumClockSkew` bounds the window a divergent clock opens in a revocation. The issue instant is stamped by the node that mints and the boundary by the node that revokes, so a minting node running ahead stamps tokens that read as later than a boundary published after them and survive it; the window is the skew between the two, and a single node whose clock steps backwards produces the same thing. The option widens the boundary by the stated amount and refuses a stamp further ahead of the verifying node than the same amount, which bounds the window at that value whatever the real skew is. It defaults to zero — the behaviour is unchanged unless it is set — and the cost when set is that a token issued within the window after a revocation is refused as well
- `RedisTokenStore` publishes revocation epochs: `RevokeBefore` raises the boundary of a user, or of one device of a user, and `RevocationEpoch` reports the one a token is compared against. The boundary is kept in a `{prefix}:epoch:<user>` hash whose fields are prefixed apart, so a device identifier that happens to be the word `user` cannot write the boundary covering the whole account, and whose values are unix nanoseconds compared as decimals rather than through `tonumber` — redis Lua numbers are doubles, whose spacing at those magnitudes is 256ns, so a raise finer than that would be silently dropped. The write is a maximum, never an assignment, so a boundary already published can never be lowered by a retry or by a second revoker racing the first, and a token once refused is never honoured again. The hash adopts the deadline of the user's index set, which by construction outlives the longest-lived token the boundary can refuse, so no token can outlive the record that refuses it; a
  non-expiring token makes it persistent. `WithRevocationEpochRetention` floors that lifetime for a user revoked while holding no token
- `Lookup` reads the token and the boundaries governing it in one round trip. The epoch key is derived from the payload, so it is built inside the script from an `ARGV` prefix and lands in the same slot through the shared hash tag. The comparison is made in Go rather than in Lua, for the same double-precision reason, and the decode is wrapped in `pcall` so a payload that is not valid JSON reaches the caller as the decode error rather than as an opaque `EVAL` failure. Note that `EVAL` counts as a write, so this read can no longer be served by a replica; nothing here enables replica reads today
- `WithTokenStoreClock` supplies the clock stamping a token's issue instant, and `RegisterTokenStoreService` resolves the container's clock into it, so the value a revocation is compared against comes from the same clock the rest of the application reads and a frozen clock in a test freezes issuance with it. An explicit option still wins over the resolved one. `EpochRevocableTokenStoreMustFromResolver` resolves the same registration and requires the epoch surface, saying so when it is absent rather than leaving a caller silently without revocation
- server-sent event backplane: `WithServerSentEventBackplaneCallTimeout` bounds one `Publish` round trip (default 1s) so a request broadcasting an event fails fast instead of hanging on an unresponsive store — the caller is typically an http handler whose context carries no deadline. A non-positive value falls back to the default. The timeout derives from the backplane's own context, so `Close` cancels an in-flight publish too

### Changed

- `Locker` — **Behavioural change**: every door of a lock — `Acquire`, `Release`, `Refresh` — is bounded at the default call timeout, one second per round trip, by capping the caller's runtime context; a store that does not answer within it is refused with the deadline in the error's chain, where before the call waited the client's own connection timeout, five seconds at the provider's default. A caller that already carries a tighter deadline keeps it, which is what the framework's `RunExclusive` and `LeaderGate` hand their renewals and releases. `WithLockerCallTimeout` moves the budget
- `NonceGuard` — **Behavioural change**: `Remember` is bounded at the default call timeout, one second per round trip, by capping the request context; a store that does not answer within it is refused with the deadline in the error's chain, which the internal-auth token source reports as the infrastructure failure it is, where before the Lua record waited the client's five seconds and the read-only existence check behind a non-positive ttl waited without end. `WithNonceGuardCallTimeout` moves the budget
- `RedisTokenStore` — **Behavioural change**: every door is bounded at the default call timeout, one second per round trip. A store that does not answer within it is refused — the context-less doors panic with the deadline in the error's chain, the way they do on any store failure, and `Lookup` and `RevocationEpoch` return it — where before a write waited the client's five seconds and a read waited without end. `WithTokenStoreCallTimeout` moves the budget
- `cache.Backend.Close` now ends the backend: every later operation answers `cache backend is closed` instead of serving over a client whose owner already tore this backend down, which is the answer the in-memory backend behind the same contract gives. A handle minted by `BackendService.WithContext` reads its owner's flag too, so the service's `Close` reaches the per-request handles the runtime door mints. The shared client itself is still not closed here; it belongs to whoever built it
- `cache.Backend.ClearByPrefix` refuses the empty prefix instead of reading it as the whole namespace. A prefix assembled at run time that comes out empty — `"tenant:" + an unresolved id` — selected everything and wiped it, which is the one outcome a prefixed delete exists to prevent. A caller that means the whole namespace has `Clear`, which says so. **Breaking** for a caller that relied on the empty prefix as a synonym for `Clear`
- a batch failure names one key deterministically rather than whichever the map yielded. `SetMultiple` walked its items in map order, so the same wrong batch named a different key on every call and hid that the entries after the first also failed; both it and `DeleteMultiple` now collect every failing key, name the sorted first, and report how many failed against how many were requested
- `RedisTokenStore.PutWithTtl` refuses a non-positive ttl instead of storing the token with no expiry. The likeliest caller of a ttl that is zero or negative computed a remaining lifetime that had already elapsed, and the silent `pttl = "0"` fallback stored exactly the token that was asked to expire forever — the same refusal the in-memory store now makes. **Behavioural change**: a caller that relied on `ttl <= 0` meaning "no expiry" must call `Put`, which is that contract's name
- `WithTokenStoreMaximumClockSkew` and `WithRevocationEpochRetention` refuse a negative value instead of silently ignoring it. Ignored, the operator who configured a policy believes it is in force while the default runs — and a skew or retention carried negative would each NARROW a revocation, which is why the silence was the dangerous half. A zero retention still reads as "keep the default"; a zero skew still disables the allowance. **Behavioural change**: a boot that passed a negative value now fails at construction instead of running the default in silence

### Fixed

- `README.md`, `timeout_config.go` — `TimeoutConfig` was described as "connect / command timeouts" with `CommandTimeout` defaulting to 3s, where the field bounds only the provider's own ping, at boot and through `Ping`, and reaches no other command; the README of the two frozen majors said so already and this one now says the same, naming `ClientConfig.ConnWriteTimeout` as the ceiling an ordinary command answers to and the per-call timeouts of the services as what ends a read
- `WithTokenStoreContext` says what it keeps: the values of the context it is given, with its cancellation and deadline dropped on purpose, since the store outlives whatever built it. The README lists it, beside `WithTokenStoreScanCount` and `WithTokenStoreClock`, which it did not
- `cache.WithMaxKeyLength` says the bound is measured on the key the caller hands in, before the prefix is put in front of it
- the boot ping ran with **no deadline at all** when the connect timeout was left non-positive. A `TimeoutConfig` naming only the command timeout put the ping on a context carrying no deadline, so a store that accepted the connection without answering hung boot forever holding a client no one could close yet. `resolveConnectTimeout` now reads a non-positive value as the default rather than as unbounded, the way `Ping` reads its own zero. The test that covered this path asserted the opposite behaviour in its name and has been renamed with the guard it now describes
- the rate limiter's window is re-armed on a key that reached the store carrying no expiry. The script armed the expiry only on the call that created the counter, so a key that lost its ttl — a `PERSIST`, an eviction policy that dropped it, a writer that set it by hand — never lapsed: the counter climbed past the limit and stayed there, and under the fail-closed default every request keyed on it was refused permanently, with nothing in the application able to lift it
- a rate limiter store failure reaches a channel when no error observer is wired. `Allow` answers a bool and `Reset` answers nothing, so an outage refused every call and was reported nowhere at all — no record, no error, no metric — and the shipped default wires no observer. The failure is now recorded at the one place that knows the key and the failure mode, and marked already-logged so the http sites do not file it a second time; an observer given by the application still replaces the record rather than adding to it, and gets the error untouched and unmarked
- the caller's own cancellation is no longer reported as a redis outage. A client that disconnected while the round trip was in flight surfaced as a store failure against a perfectly healthy store; it is now named apart, and recorded at warning rather than error, while the call-timeout deadline stays a store failure because that budget exists to catch the store being slow
- a negative ttl is refused instead of storing the entry forever. It fell into the branch that writes no expiry at all, so the one value the caller meant to be short-lived was the one value stored without end; `SetMultiple` judges it before its empty-batch early return, the order the in-memory sibling judges it in. Zero still means no expiry, as both backends document
- `Clear` and `ClearByPrefix` scan every node of the client rather than the one connection a single command reaches. Against a cluster the scan reported only one node's slice of the keyspace, so a wipe deleted that node's share and reported success — the caller read a complete invalidation from a partial one
- a multi-batch wipe that fails part-way is described at the operation's extent rather than the failing batch's. The batches before it are irreversibly gone, and counts covering only the failing batch could not say whether the wipe destroyed nothing or nearly everything
- the counter refusals are named the way the in-memory sibling names them: a value that is not an integer, a delta that overflows when negated, and a counter driven past the int64 ceiling arrived under one message that is also the message of a store outage, so neither the operator nor the application could tell a bug in the call from redis being down. The store error stays the cause in every branch
- every key refusal names the key it is about, and a batch read that cannot decode an entry names it too. A batch call validates the keys the caller handed in as a set, and a refusal that does not say which of them is malformed leaves nothing to act on

- `DeleteByUser` no longer claims to revoke every live token a user holds. `SSCAN` does not promise to return a member added while the walk is in progress, so a token issued after the walk passed the bucket it lands in survived the call — and the documentation said otherwise, which is how a reader came to believe the walk was sufficient. It is now documented as cleanup, with `RevokeBefore` named as what ends a user's sessions
- `PurgeExpired` walks each user index in bounded batches rather than reading it whole inside one script, so maintenance no longer blocks every other client of that Redis for as long as the set is large — measured at two seconds for a million tokens against under three milliseconds for the longest batch now. It also counts what it actually removed rather than what it found, since a shrinking set can hand the same member back to a later batch
- the per-user token index carries an expiry that outlives the longest-lived token it lists, so revoking by user no longer walks a set that grows without bound. The index was created without one and never pruned, while the tokens it named expired underneath it
- `DeleteByUser` revokes in bounded batches rather than reading the whole index in one script. A single script over a large index blocks every other client of that Redis for as long as it runs — measured at 2.86 seconds for a million tokens; the longest batch is now 7.7 milliseconds for the same set
- `provider.go` — transient-error detection recognises a connection abort through explicit markers for both spellings its platforms give it (`software caused connection abort` and `established connection was aborted`), aligning with the bunorm providers

## [v3.5.1] - 2026-07-24 - Reconnect Backoff Clamps

### Fixed

- a `ReconnectConfig.BackoffFactor` below 1 (or NaN) falls back to the default instead of decaying the server-sent-event backplane's resubscribe backoff toward zero and busy-spinning through a redis outage
- a `ReconnectConfig.InitialBackoff` above `MaxBackoff` (a units typo, such as minutes against a seconds cap) is clamped onto the cap, so the first resubscribe wait can no longer exceed the declared maximum
- an extreme `BackoffFactor` (huge or `+Inf`, which passes the at-least-1 guard) overflows the backoff product into a negative duration; the growth step collapses a non-positive result onto `MaxBackoff` instead of resubscribing with a zero delay

### Changed

## [v3.4.1] - 2026-07-17 - Rate-Limiter Call Timeout and Retry-Backoff Clamps

### Fixed

- `rate_limit.go` — `RateLimiter.AllowWithRuntime` now applies the configured call timeout. It passed the runtime context straight through, and melody's http kernel attaches no deadline to a request context, so `WithRateLimiterCallTimeout` was dead on the exact path every http middleware uses: a Redis TCP black-hole (a partial partition, not a clean refusal) made every gated request hang under the recommended `FailureModeClosed` instead of failing fast. The runtime context is now capped with the call timeout (`context.WithTimeout` keeps the earlier deadline, so a request carrying a tighter one still wins), governing both entry points.
- `provider.go` — the connection retry backoff rejects degenerate values: a non-positive `InitialDelay` or `MaxDelay` and a `BackoffMultiplier` that is not at least 1 — a NaN included, which fails every comparison and so slipped through a below-1 check, poisoned the float-space growth and converted to a negative duration — fall back to the defaults instead of collapsing every retry into an immediate re-dial (a negative delay made the sleep return immediately; a sub-1 multiplier decayed the delay toward zero). A multiplier of exactly 1 remains a valid constant backoff.

## [v3.4.0] - 2026-07-11 - Distributed Rate Limiter and Forwarded-Client-IP Resolver

### Added

- `rate_limit.go` — `NewRateLimiter(client, limit, window, options...)`: a Redis-backed fixed-window rate limiter implementing both `http/contract.RateLimiter` and the new `http/contract.RuntimeRateLimiter`, so N application instances enforce one shared limit — the distributed drop-in for the in-process middleware limiters, whose per-replica counters make a login rate limit meaningless behind a load balancer. The counter is one atomic Lua round trip (`INCR` + `PEXPIRE` on creation); the fixed window admits up to 2x the limit across a window edge. Store failures follow a configurable policy defaulting to fail-closed (deny when Redis is unreachable) — `WithRateLimiterFailureMode(FailureModeOpen)` selects availability instead; `WithRateLimiterOnError` observes failures on the void `Allow` path, `WithRateLimiterCallTimeout` (default 250ms) bounds it, and `WithRateLimiterKeyPrefix` namespaces the keys. Requires melody/v3 with `RuntimeRateLimiter` (unreleased at the time of this entry).

### Fixed

- `lock.go` — `Acquire` now fails closed on a non-positive ttl instead of writing a key with no expiry. A Redis lock is a lease: its expiry *is* the crash safety, so a ttl of zero produced a key that outlived the holder forever — after a `SIGKILL` or an out-of-memory kill, every later acquirer on every instance skipped its work silently, with no error and no expiry to recover from. Session-style locks (hold until the connection drops) remain the MySQL `GET_LOCK` and PostgreSQL advisory backends, whose `Refresh` is a liveness probe; this backend no longer pretends to offer them. The acquire script is correspondingly simpler — it always sets `PX`.
- `rate_limit.go` — `WithRateLimiterCallTimeout` falls back to the default call timeout for a non-positive duration instead of building an already-cancelled context. That context forced every `Allow`/`Reset` onto the store-failure path — deny-all under `FailureModeClosed`, allow-all under `FailureModeOpen` — no matter whether Redis was actually reachable.

## [v3.3.0] - 2026-07-06 - Redis-Backed Nonce Guard and Provider Open Retry

### Added

- `v3/nonce_guard.go` — `NonceGuard` (`NewNonceGuard(client)` / `NewNonceGuardWithPrefix(client, prefix)`) is a Redis-backed implementation of the core `security/contract.NonceGuard`, the replay-protection guard for the internal-auth HMAC token source. `Remember` runs a single atomic `SET NX PX` Lua script that records a nonce only when absent and returns whether it already existed, so a nonce replayed against any application instance is detected (which the core in-process `MemoryNonceGuard` cannot do across instances). A non-positive ttl performs a read-only existence check — reporting whether the nonce is currently recorded — without storing, matching the in-process `MemoryNonceGuard` at the acceptance-window edge rather than reporting a still-recorded nonce as fresh. Requires the core `melody/v3` version that introduces `security/contract.NonceGuard`.
- `v3/retry_config.go`, `v3/provider.go` — `WithRetryConfig(RetryConfig)` provider option (plus `RetryConfig`, `DefaultRetryConfig()`, `NewRetryConfig(maxAttempts, initialDelay, maxDelay, backoffMultiplier)`) makes `Provider.Open` re-dial the initial connection with capped exponential backoff on transient failures (connection refused, no such host, i/o timeout, network unreachable, `EOF`/closed-connection during the handshake, …), so an application racing a cold-starting redis container no longer hard-fails at boot. The backoff is computed in float space and capped at `MaxDelay` before the `time.Duration` conversion, so a very high `MaxAttempts` cannot overflow the delay to a negative value that collapses the backoff. Only transient errors retry — a real misconfiguration (for example a bad password) still fails fast. Mirrors the `bunorm/mysql/v3` provider's retry. Opt-in: without the option `Open` behaves exactly as before.

### Fixed

- `provider.go` — `isTransientError` now also classifies a Redis `LOADING` reply (`LOADING Redis is loading the dataset in memory`, returned while a restarted server replays its RDB/AOF before accepting commands) as transient, so `WithRetryConfig`'s `Open` retry covers the cold-start window it targets rather than hard-failing the moment the server accepts connections but is not yet ready.

## [v3.2.0] - 2026-06-16 - Redis Lock, Revocable Token Store, and Server-Sent Events Backplane

### Added

- `v3/service_resolver.go` + `v3/cache/service_resolver.go` — plug-and-play container registration: `RegisterClientService` (registers the Redis client under `ServiceClient`, with `ClientMustFromResolver`/`ClientMustFromContainer`), `RegisterLockerService` (under the core `lock.ServiceLocker`), `RegisterTokenStoreService` (under `ServiceTokenStore`, with `TokenStoreMustFromResolver`), and `cache.RegisterBackendService` (under the core `cache.ServiceCacheBackend`), so an application configures the Redis client once and resolves the lock, token store, and cache backend from many services.
- `v3/module.go` + `v3/cache/module.go` — `rueidis.NewModule(ModuleConfig{Client, AsLocker, AsTokenStore, TokenStoreOptions})` and `cache.NewModule(ModuleConfig{Client, Prefix})` self-registering application modules: a single `app.RegisterModule(...)` registers the client service and, opt-in, the locker and revocable token-store services (and the cache backend), instead of calling `RegisterClientService`/`RegisterLockerService`/`RegisterTokenStoreService`/`RegisterBackendService` by hand. v3 only.
- `v3/lock.go` — Redis-backed implementation of the core `lock/contract.Locker`/`Lock`. `NewLocker(client)` creates named locks; `Acquire` runs an atomic compare-and-set Lua script that grants the lock when the key is absent **or** already held by this same token (refreshing its TTL), `Release` runs a `GET`-and-`DEL` compare-and-delete Lua script (releases only when this instance still owns the key), and `Refresh` runs a `GET`-and-`PEXPIRE` compare-and-extend script that errors when the lock is no longer held. Each lock owns a 16-byte crypto-random token so it can never release or refresh another holder's lock.
- `v3/token_store.go` — Redis-backed implementation of the core `security/contract.RevocableTokenStore`. `NewTokenStore(client, ...options)` stores JSON-encoded claims at `{<prefix>}:token:<token>` with `PX` matching the ttl (zero ttl persists) and indexes each token under its owner in a `{<prefix>}:user:<id>` set. The whole keyspace is pinned to one Redis Cluster slot through the `{<prefix>}` hash tag, so the multi-key `Put`/`Delete` Lua scripts — which also touch the per-user index, including the previous owner's index set when a token is re-issued to a different user, a key the script computes dynamically and so cannot pre-declare — never raise `CROSSSLOT` on a cluster deployment. `Put`/`Delete`/`DeleteByUser` use Lua so the token key and the user index stay consistent in one round trip — including re-indexing when a token is re-issued to a different user. `DeleteByUser` returns the count of live tokens revoked and drops the set (members whose key Redis already expired are not
  counted but are still cleaned). `PurgeExpired` reconciles the user index by pruning members whose token key has already expired (Redis expires the token keys natively; it returns the number of stale members pruned). The context-less mutators use a constructor-bound context (`WithTokenStoreContext`, default background) whose cancellation is detached via `context.WithoutCancel` — values carry through but a cancelled parent can never permanently brick the mutators; `Lookup` uses the per-request `runtime.Context()`. The key namespace is configurable via `WithTokenStorePrefix` (default `melody:token`).
- `v3/server_sent_event_backplane.go` — `NewServerSentEventBackplane(client, hub, ...options)` is a Redis pub/sub backplane for the core `http.ServerSentEventHub`, so Server-Sent Events/WebSocket broadcasts fan out across every application instance behind a load balancer instead of reaching only the instance that emitted them. Each broadcast is published to a shared channel (`WithServerSentEventBackplaneChannel`, default `melody:sse`) tagged with a per-instance random origin; a dedicated subscription forwards other instances' events into the hub via `DeliverLocal` and ignores the echo of its own origin, so no event is delivered twice. The subscription re-establishes itself with bounded backoff (1s→30s) after a connection drop; `Close` stops it and detaches the backplane from the hub (`SetBackplane(nil)`), so a `Broadcast` issued after `Close` is no longer replicated to a torn-down backplane on a cancelled context (which would otherwise keep incrementing `BackplaneFailures()`). The
  Redis client is caller-owned and is not closed. `WithServerSentEventBackplaneLogger` surfaces subscription/decode failures.
- `v3/README.md` — added a v3 module README documenting the client `Provider`, the distributed `Locker`, the revocable `RedisTokenStore`, the `ServerSentEventBackplane`, the `cache` backend, and the plug-and-play `Register*` helpers, and documented that the `rueidis.Client` is owned by the application and that `cache.Backend.Close` does not close it, so a single client can be shared across the cache, locker, token store, and backplane.
- `v3/reconnect_config.go` — `ReconnectConfig` (`InitialBackoff`, `MaxBackoff`, `BackoffFactor`) with `DefaultReconnectConfig()` (the former hardcoded 1s / 30s / ×2) and `NewReconnectConfig(...)`. The Server-Sent Events backplane resubscribe backoff was previously fixed package constants; it is now configurable via the new `WithServerSentEventBackplaneReconnectConfig(*ReconnectConfig)` option, with zero fields inheriting the defaults so existing behaviour is unchanged.
- `v3/token_store.go` — `WithTokenStoreScanCount(int)` option exposes the `PurgeExpired` SCAN cursor batch size (previously a hardcoded `256`); zero keeps the default.
- `v3/cache/backend.go` — `WithMaxKeyLength(int)` option on `NewBackend(...)` / `NewBackendService(...)` exposes the cache-key length guard (previously a hardcoded `1024`); zero keeps the default. The constructors keep their existing positional signatures and take the limit as a trailing functional option (`BackendOption`), so existing callers compile unchanged.

### Fixed

- `v3/provider.go` — `Provider.Open` no longer fails against a healthy Redis when a caller-supplied `TimeoutConfig` leaves `ConnectTimeout` at zero. The startup ping built `context.WithTimeout(…, 0)` — an already-expired context — so any partial config (for example one that only sets `CommandTimeout`) made `Open` return `redis connection failed` (`context.DeadlineExceeded`) every time. A zero or negative `ConnectTimeout` now pings without a deadline, matching the `bunorm` mysql/pgsql providers' connection-ping guard. Regression coverage in `v3/provider_test.go`. The `v2/provider.go` provider received the same guard.
- `v3/cache/backend.go` — `Clear`/`ClearByPrefix` now glob-escape the literal key prefix before appending the `*` wildcard for `SCAN MATCH`. Keys are stored with the prefix as a literal string, but `SCAN MATCH` interprets `*`, `?`, `[`, `]`, and `\` as glob metacharacters, so a prefix (or a `ClearByPrefix` argument) containing one of them produced a pattern that no longer matched the stored keys — silently skipping the delete — or over-matched and deleted siblings. The literal prefix is now escaped while the trailing prefix-match `*` stays literal.
- `v3/token_store.go` — `DeleteByUser` no longer revokes another user's live token. The user-index set member is only re-pointed away from the previous owner inside the `if existing` branch of the put script, so when a token string's prior value had already TTL-expired before the same string was re-issued to a different user, the stale membership lingered in the old owner's set — and `PurgeExpired` could not prune it (the token key exists again). `DeleteByUser` then deleted that token (now owned by the new user) and counted it for the wrong user. `tokenDeleteByUserScript` now re-reads each member's stored `UserIdentifier` and deletes only tokens still owned by the requested user, so a stale index member can no longer cross-revoke.
- `v3/lock.go` + `v3/token_store.go` — a positive but sub-millisecond TTL is now floored to 1ms instead of truncating to `0` via `time.Duration.Milliseconds()`. A `0` reached Redis with three different broken outcomes: the token store's persist branch treated `"0"` as "no expiry", so a token meant to expire was stored **permanently**; `Lock.Acquire` built `SET … PX 0`, which Redis rejects (`invalid expire time`), so the acquire failed instead of taking a short-lived lock; and `Lock.Refresh` ran `PEXPIRE key 0`, which deletes the key immediately, silently dropping the lock while the holder still believed it held it. A shared `floorPositiveMilliseconds` helper guarantees a positive TTL never collapses to `0`.
- `v3/lock.go` — `Acquire` is now reentrant for the same lock instance, matching the in-memory locker's behaviour that the shared `lock` contract asserts (and tests). The previous `SET … NX` returned `false` on a re-acquire of a lock this instance already held; a caller reading that as "not held" would skip `Release` and orphan the key until its TTL elapsed (or forever for a non-expiring lock). The compare-and-set Lua script now re-grants and refreshes the TTL when the key already holds this token.
- `v3/cache/backend.go` — `SetCtx`/`SetMultipleCtx` now floor a positive sub-millisecond TTL to 1ms. rueidis derives the `PX` argument as `int64(ttl/time.Millisecond)`, so a positive ttl below 1ms became `SET … PX 0`, which Redis rejects (`invalid expire time`) — failing the whole write — whereas the in-memory backend accepts the same ttl. Flooring keeps the two backends consistent (mirrors the existing `floorPositiveMilliseconds` guard on the lock and token store).
- `README.md` — the v3 plug-and-play section resolved the cache backend with `cache.CacheMustFromResolver` (service `cache.ServiceCache`), but `cache.RegisterBackendService` registers only `cache.ServiceCacheBackend`, so following the documented wiring would panic at resolution. The README now resolves the backend with the matching `cache.CacheBackendMustFromResolver`.
- `v3/cache/backend.go` — `Backend.Close` no longer closes the caller-provided `rueidis.Client`. The client is created by the application and shared across the cache backend, the distributed `Locker`, the revocable `RedisTokenStore`, and the `ServerSentEventBackplane` (as the README and `.example` wiring show — all four take the same `client`); closing it from the cache backend tore the connection out from under the other three. `Close` is now a no-op, matching the locker, token store, and backplane (none of which close the shared client) and the framework convention that resource lifecycle is owned by the application, which closes the client once at shutdown.
- `v3/token_store.go` — `PurgeExpired` now glob-escapes the user-index key prefix before appending the `*` wildcard for `SCAN MATCH`, mirroring the cache backend (which was already hardened for this). The prefix is configurable through `WithTokenStorePrefix`, so a value containing a glob metacharacter (`*`, `?`, `[`, `]`, `\` — for example a tenant prefix like `app[eu]`) produced a `SCAN MATCH` pattern that no longer matched the stored per-user sets, so `PurgeExpired` silently pruned nothing and stale set members accumulated. The literal Lua `KEYS` usages are unchanged; only the scan pattern is escaped.
- `v3/server_sent_event_backplane.go` — the `listen` subscription loop no longer busy-loops when `Receive` returns without an error before its context is cancelled. Only the error path backed off; a clean early return (rueidis documents `Receive` returning `nil` on an unsubscribe) reset the backoff and immediately re-subscribed with zero delay, spinning the goroutine at full CPU if the condition recurred. Every re-subscribe is now rate-limited by the backoff, and the backoff is reset only after a subscription that ran for at least the initial-backoff duration (a productive subscription), so a healthy long-lived connection still reconnects fast.

## [v3.1.0] - 2026-04-20 - Additive Ctx-First Cache Backend API

### Added

- `cache/backend.go` — additive ctx-first surface on `*Backend`: `GetCtx`, `SetCtx`, `DeleteCtx`, `HasCtx`, `ClearCtx`, `ClearByPrefixCtx`, `ManyCtx`, `SetMultipleCtx`, `DeleteMultipleCtx`, `IncrementCtx`, `DecrementCtx`. Each takes `ctx context.Context` as the first parameter so caller deadlines / cancellation propagate end-to-end. - `cache/backend_service.go` — `BackendService.Backend()` accessor exposes the underlying `*Backend` for callers that want to invoke the ctx-first surface directly without rebinding; mirrored in `v2/` and `v3/`
- `cache/backend_service_test.go` — reflection assertions that `Backend` retains its stored `ctx` field, that the eleven `*Ctx` methods exist with the agreed signatures, and that the legacy methods are preserved unchanged; compile-time `var _ func(...)` assertions pin both surfaces; mirrored in `v2/` and `v3/`

### Deprecated

- `cache.Backend` — ctx-less methods (`Get`, `Set`, `Delete`, `Has`, `Clear`, `ClearByPrefix`, `Many`, `SetMultiple`, `DeleteMultiple`, `Increment`, `Decrement`) are now marked `// Deprecated: prefer <NameCtx>, which takes ctx per call.` They continue to work by delegating to the `*Ctx` methods with the stored ctx, but new code should adopt the ctx-first API (MEL-165); mirrored in `v2/` and `v3/`
