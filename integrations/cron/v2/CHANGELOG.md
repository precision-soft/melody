# Changelog

All notable changes to `precision-soft/melody/integrations/cron/v2` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- **Breaking (generation-time refusal):** the user-less crontab dialect refuses a day-field pair busybox crond — the scheduler that dialect targets — runs as a different schedule than vixie crond and the in-process runner. Busybox classifies a day field by its expanded values (a field admitting every value is unused and the other field alone governs; measured on busybox 1.37, where `0 0 16 * 0-6` runs only on the 16th while the crontab-dialect matcher answers due every day), vixie by the spelling's first character, and the generator used to emit the pair without a word. The check is semantic — both models evaluated over every day combination — so a pair the two daemons read identically, a stepped wildcard beside the plain one included, still renders; the refusal names the entry, both spellings and the rewrite, and `ErrBusyboxDivergentDaySchedule` is its sentinel. The `/etc/cron.d` dialect keeps rendering the pair, since vixie reads it exactly as the runner does
- **Behavioural:** the scheduler loop's per-minute document reports the evaluated minute as the real local instant — offset and all — instead of the utc materialization of its wall fields, which stated an instant off from the truth by the whole zone offset and disagreed with `--once`, which always reported local time. Only the minutes a forward jump skipped, the span a daylight-saving spring-forward has no local representation for, stay utc-materialized in the catch-up evaluations
- the generator creates the subdirectory an `EntryConfig.LogFileName` names ("nightly/report.log"), the same way it always created the destination's parent: the name passed the escape guard, nothing created the directory, and under system cron the shell aborts the whole command when the `>>` redirection cannot create its file — so the scheduled job silently never ran while the same configuration ran fine in-process

### Added

- `melody:cron:run --report-idle` makes the scheduler loop report every evaluated minute instead of only the ones that dispatched a command, so a consumer can tell a live scheduler with nothing due from a dead one
- `UserColumnTemplate` — the optional capability of answering whether a dialect renders a user column, read before anything is rendered because the generator has to know whether a heartbeat line needs a user before it places one. The decision was taken on the name of a builtin, so a dialect registered through the documented extension door and rendering no user column — the Kubernetes example in this very README among them — was refused for a crontab user it would never have rendered. A template that does not implement it is judged by name, as before
- `OwnedTemplate` — the optional capability of naming a line every destination a template renders carries, by which a later run recognizes a file as one of its own. It exists for `--prune`, which has to answer "did I write this?" about a file it is being asked to empty, and the only honest answer comes from the rendered content: the marker cannot be injected by the generator, because `Render` is userland and a comment prefix that is right for a crontab corrupts a format that has no comments. Both built-in dialects implement it and render `CrontabOwnershipMarker` in their header block; a template that does not implement it is never pruned
- `melody:cron:generate --prune` empties the destinations in `dir(--out)` that this generator wrote earlier and this run no longer produces. Three rules bound it, because emptying a file is not reversible: it is opt-in, it reads only the output directory and never a destination an entry placed elsewhere by absolute path, and it touches only a file whose head carries the current template's ownership marker. Emptying means re-rendering with no entries, so the destination keeps its marker and stays recognizable to the next run. An empty configuration sweeps too — that is precisely the version in which every previously written destination is stale — and the run stays the success it always was
- the json envelope carries `data.pruned`, the destinations the sweep emptied, as a list on every run rather than a field whose type changes with the outcome

- `EntryConfig.Arguments` carries the entry's own command-line arguments wherever that entry runs: the in-process runner hands them to the child command and the generator renders them into the manifest line. This is where a job declares its own output posture — `Arguments: []string{"--format=json"}` — because the runner has no posture to lend it and every job decides its own; the dispatch used to hand the child nothing but its command name, so every job ran on the declared defaults of its flags whatever the entry configured. `EntryConfig.Command` remains the other thing: a whole shell line replacing the binary and the command name, which only the generated manifests can run

- every run of a scheduled command carries the console identity the cli entry point installs for its own runs: a fresh `ProcessContext` under a per-run id and a logger that keeps the runner's `processId` while adding the run's `cronRunId`. A command reading the documented console doors — `ProcessContextMustFromResolver` above all — worked launched by hand and failed under `melody:cron:run` on every tick, because the run's child scope is a sibling of the console scope and inherited nothing; and overlapping runs of one entry were indistinguishable in the log
- both commands carry the standard flag set every melody command accepts, and `melody:cron:generate` renders its summary as the single machine-readable document under `--format=json`. The framework rewrites `-v`/`-vv` into `--verbosity` for every command, so the two commands that declared no standard flags died on the framework's own convention with "flag provided but not defined"
- a scheduled command can run under a deadline. `EntryConfig.Timeout` bounds one run; without it a run is unbounded, which is what every entry configured before this existed already had and what an entry whose duration is genuinely open-ended keeps. Reaching the deadline cancels the command's context — a signal, not a kill — and a command that watches it unwinds and reports its own error alongside the timeout. Only a command that ignores the cancellation for a whole `EntryConfig.GracefulTimeout` (five minutes by default, per entry) is abandoned: the overrun is reported at warning naming the entry and both windows, its container scope is closed under it so the resources it holds are given back, and it stops counting towards the shutdown wait. That last step is a kill and is documented as one — `scope.MustGet` panics on a closed scope, and a panic in a goroutine the command started itself is beyond any recover, which is why the window before it is measured in minutes

### Changed

- `generate_command.go` — a relative path that comes from a PARAMETER is anchored at the project directory, the way every other melody runtime path is; one typed as a cli FLAG stays relative to the working directory, which is the shell's own convention. `melody.cron.logs_dir = var/log/cron` meant a different directory depending on where the binary was invoked from — under a supervisor starting from `/`, the generated crontab baked `/var/log/cron` into itself and the run reported success — while `MELODY_LOG_PATH`, `kernel.logs_dir` and `kernel.cache_dir` have been resolved against the project directory all along. The shipped defaults hid it by carrying `%kernel.project_dir%` themselves, and a configuration that names no project directory keeps the previous anchoring. **Behavioural change**: a deployment whose cron parameters carry relative paths and whose working directory is not the project directory now writes elsewhere — see the framework's `UPGRADE.md`

- `generate_command.go` — `RegisterTemplate` states its replacement contract: it installs under the template's name and replaces an existing one silently, the door through which an application overrides a builtin dialect; two application templates sharing a name resolve to the later registration, so a caller that must not replace anything checks the name first
- `module.go` — a `ModuleConfig` carrying `RunnerCommands` but no configuration is refused at registration with a named panic, and so is a `ConfigurationFactory` that returns nil: accepted, the module silently registered nothing and the operator discovered the wiring error as "unknown command" at invocation — the exact failure mode `migrate.RegisterCommands`'s own refusal names as its reason. A nil configuration stays legal only while the module genuinely has nothing to register, and the factory's precedence over `Configuration` is now written on the fields. **Breaking** at boot for a wiring that silently registered nothing until now
- README — the configuration cascade names its two in-command fallbacks — `--template` falls back to the crontab dialect and `--binary` to the running executable — instead of claiming no hardcoded fallbacks exist while the table below documented one of them
- README — the per-command overrides table states the runner's real defaults: a `Timeout` left at zero means no deadline at all, not the one hour the table claimed (an hour is a suggestion in the prose, not a default), and an abandoned command is reaped one `GracefulTimeout` after the deadline — five minutes by default, not five seconds — with the `GracefulTimeout` override now carrying its own row. An operator relying on the documented one-hour bound in fact had no bound at all
- `runner_command.go` — an entry routed to another crontab file (`EntryConfig.DestinationFile`) joins the construction refusal beside its siblings `Command` and `Instances`: such an entry addresses an external scheduler, and accepted by the runner as well it executed twice — in-process and in the generated crontab — whenever both were live. **Breaking** at boot for a configuration that silently double-ran until now
- `generate_command.go` — a `melody.cron.heartbeat.enabled` value that does not hold a boolean fails generation instead of being read as "not enabled". The conversion error was discarded, so a typo produced a crontab with no liveness line and a success message, leaving a misspelled opt-in indistinguishable from never having asked for one — while every other configuration mistake on this command (missing output path, missing user, bad schedule) is a hard error. **Breaking** at runtime for a configuration carrying a malformed value.

### Fixed

- the readme's sample crontab shows the header the renderer actually writes: the ownership marker line (`# owned by melody:cron:generate`) and the nine-line job-definition comment section were missing from the "Producing:" artifact, so a reader diffing their generated file against the documented one — or building tooling around the documented head — got a shape the generator never produces, while the prune section of the same document asserts the marker is rendered in every header block
- the readme's binary-resolution section names the consequence of `os.Executable()` resolving symlinks: on a deployment publishing releases behind a `current` symlink, the fallback pins the release directory the generator ran from, so the manifest keeps executing that release's binary until the directory is pruned and answers `No such file or directory` after. The documented remedy for that deployment shape is passing the symlinked path explicitly through `--binary` or `melody.cron.binary`
- `melody:cron:generate --prune` no longer opens whatever the output directory holds that is not a directory: the sweep considers regular files only. A named pipe beside the destinations wedged the generator inside `os.Open` with no deadline and no diagnostic — measured, it never returned — and a device, a socket or a symlink is refused for the same reason, since this generator wrote none of them and none of them can be one of its own
- `melody:cron:generate --prune` in text mode names the destinations it already emptied when the run fails part way through, the way the json rendering beside it always has. Emptying is irreversible and the sweep hands back what it emptied beside its failure, so returning early left the operator of a broken deploy with manifests blanked and not one line saying which — no `pruned` line, and not even the `wrote` lines of the writes that had succeeded
- `melody:cron:run` classifies each run once instead of twice. `isShutdownCancellation` was consulted for the document row and again for the record and the failure aggregate, reading the runtime's context both times, so a SIGTERM landing between the two reads made the row report `failed:true` while the branch below treated the same run as a clean stop, kept it out of the aggregate and let the process exit 0 with `error:null` — one run with two verdicts. The row's own answer is now the one the record and the aggregate use
- `data.ran[].arguments` is a list on every row of the `melody:cron:run` document, empty rather than null for an entry that declares no arguments — which is most of them. A field whose json type changes with the outcome cannot be consumed at all: `jq '.data.ran[].arguments | length'` died on the first argument-less job. It is the rule this command's own document already keeps for `error`, `ran`, `failed` and — in the generator — `pruned`, each through a normalizer of its own; `arguments` was the one field of the row left on nil
- the documents of `melody:cron:run` are one line each, which is what this README has promised since the envelope landed: the framework's json printer no longer indents, so a scheduler followed with a line reader receives one closed document per line instead of a twenty-line block per minute that every line-framed consumer parsed as fragments. `--format=json-pretty` renders the same document indented for reading by hand. See the framework changelog for the printer itself

- `melody:cron:run` writes the document its declared flags always promised, and says what it drives before it drives anything. The command declared and validated `--format=json` through `StandardFlags` and then answered zero bytes on every path, so a deploy step spelled `app melody:cron:run --once --format=json | jq` received an empty stream — indistinguishable, to the step reading it, from a missing binary — and the only observable effect the flag had was that the cli banner disappeared. Every dispatched minute now renders the same envelope every other melody command renders: the minute, the configured entry count and each run with its schedule, arguments, run id, duration and verdict, with the aggregated failure inside the envelope's error. `--once` writes exactly one document and exits; the scheduler loop writes one per minute that dispatched something, silent on the idle ones unless `--report-idle` asks for them. Beside it, a record at the head of every run names how many entries the runner drives and the schedule of each — at **warning** when the number is zero, mirroring the generator's own `nothingToWrite`, because a scheduler built over a configuration emptied by a refactor used to run forever, exit successfully and write nothing anywhere
- a scheduled command that panics keeps its whole cause chain in the record. The recovery boundary joined its rich error onto the run error, and `errors.Join` answers an `Unwrap` of `[]error` while `exception.LogContext` anchors the record's `cause` and `causeChain` on `errors.Unwrap` — the single-value form — so a job panicking through melody's own idiom filed a record carrying the top message and nothing under it: not the context naming the parameter, not the chain naming the connection that refused. The operator could not tell an outage from a credential change from a wiring fault, which is the whole of the classification. The same fix covers the three other joins on the run path — the child scope close, and the two deadline branches, where the classification and the command's own failure now share one single-valued chain so both stay reachable by `errors.Is`
- the json envelope of `melody:cron:generate` carries the failure's own context under `error.details` and the whole chain under `error.cause.details.chain`. Both were `nil` on every failure alike, so the machine document — the one a deploy pipeline reads — was the single rendering that threw away what the error already carried: a failed rename filed the destination and the source in the journal at the same instant and answered `"details":null,"cause":null` on stdout
- a malformed schedule names the field that failed, the limits it was judged against and — where a dialect chose those limits — the dialect. `Schedule{DayOfWeek: "7"}` under the kubernetes dialect failed the boot with `expression:"7"` and `reason:"value is out of range"`, telling the operator neither which of the five positions was refused nor that `7` is a perfectly legal Sunday under the crontab dialect the same configuration would generate for. The generator's own validation, whose bounds are dialect-independent, names no dialect rather than one that never chose

- the generator no longer leaves a destination an earlier version wrote running forever. A job the current configuration retired kept running on every tick, and a job MOVED to another destination file ran from both — the double execution `melody:cron:run` refuses at construction, produced silently here. `--prune` is the opt-in that reconciles; without it the behaviour is unchanged
- `Configuration.Entries` hands out copies all the way down — the list, each `ScheduledCommand` and each `EntryConfig` behind it, schedule included — so a caller writing through the pointer it was handed can no longer rewrite the registration and, with it, every manifest generated afterwards. Every entry the generator expands also carries its own schedule, because `Render` is userland and `Schedule.Defaults` is documented as mutating in place, so a template that called it rewrote the registered schedule for the rest of the process
- the GoDoc of `Configuration.Schedule` named the wrong consumer: the in-process runner photographs each entry's deadlines into its own run entry at construction, so a mutation landing afterwards cannot reach a scheduler already running. The generator is the consumer at risk, together with a runner built later

- `melody:cron:generate --format=json` renders one envelope on every outcome, the failures included. The one door that builds the envelope was reached only from the paths that succeeded, and the cli silences the command's own error line under json, so a deploy script piping the generator into `jq` received an empty stream — indistinguishable from a missing binary — for a malformed schedule, an unwritable directory or a template that would not render. The failure travels as `error.code = "cron.generateFailed"` with its own message as the cause, and `data.writes` still names the destinations already written: the generator writes one destination at a time with no rollback, so a failure on the third of four leaves two files on disk the consumer has to be able to learn about. In text mode the failure is reported by the cli entry point as before
- a scheduled command's own output reaches the journal instead of the process stdout. Due entries run concurrently, one goroutine each, and every one of them held the same `os.Stdout`: several jobs' reports arrived interleaved, in colour nobody asked for, and none of it reached the log file the operator reads — the runner's documented promise that it writes nothing to the command output itself was true only of the runner's own lines. Each run that printed anything now files one record naming the entry and the run id, at info when the run succeeded and warning when it did not, capped at 64 KiB with the cut counted in the record

- `runner_command.go` — a panicking scheduled command hands its panic value on as the CAUSE of the recorded failure and carries the stack of the goroutine that raised it. Stringified into the context alone, the framework's own idiom — a `MustGet` on a mistyped parameter, which panics with an error whose own context names it — reached the operator as a message and a command name, with the cause chain empty and no file or line anywhere, while the same failure inside an event listener produced the context, the chain and the stack. A typed-nil panic value answers no cause, since its `Error()` would dereference a nil receiver on the goroutine that drives every entry. **Behavioural change**: `errors.Is` and `errors.As` on the run's error now reach the failure underneath; the `panicValue` context key is unchanged

- `runner_command.go` — a run the runner's own shutdown cancelled is the clean stop the runner's documentation asks for, not a job failure: a command that watched its context and unwound when SIGTERM cancelled it was recorded as `cron runner command failed` at error and failed the `--once` aggregate, indistinguishable from a genuinely broken job, so alerting fired on every deploy. The parent's cancellation is now recorded at warning under `cron: scheduled command cancelled by shutdown` and kept out of the failure aggregate; a deadline the entry asked for stays a failure whatever the shutdown is doing. **Behavioural change**: `melody:cron:run --once` interrupted by a clean shutdown exits 0 instead of non-zero
- `runner_command.go` — the runner's records about a run — the failure line, the abandon warning — carry the run's `cronRunId`, the id minted precisely so overlapping runs of one entry stay distinguishable: a failure record tied to neither stream defeated the id at the one moment it matters
- `configuration.go` — `Schedule` copies the entry configuration instead of retaining the caller's pointer, and `Entries` hands out a copy of the list: the runner reads an entry's deadlines at every run and the generator re-reads its fields at every generation, so a caller mutating its own struct after registration changed validated behavior mid-process, as an unsynchronized write racing the scheduler goroutine's reads. **Behavioural change**: post-registration mutation of the caller's own objects is now inert
- `runner_command.go` — the runner reads a command's result through the interface the way the cli entry point always has: a command that returns its failure through a concrete error pointer hands back a typed nil boxed into a non-nil interface, and the runner read it as the failure it is not — on the dispatch goroutine, which deliberately carries no recover, so the first render of that "failure" dereferenced a nil receiver and took the whole scheduler process down with the one job. The same command runs clean under the cli entry point, whose `normalizeCliError` exists for exactly this
- `runner_command.go` — the failure record of a scheduled run carries the failure's own exception context — the panic value above all — instead of the bare message. A job that panicked at 03:00 produced a record whose only content was "cron: scheduled command panicked"; the panic value the recover had carefully stored in the error's context was dropped by the rendering, leaving nothing to debug with. The record now goes through `exception.LogContext`, the same door the framework's own integration-error paths use
- `runner_command.go` — the `--once` aggregate carries the per-command failures as its cause instead of only their names, so `errors.Is` against a sentinel — `ErrCommandTimeout` above all — answers at the process boundary the way it already answers per run
- `generate_command.go` — the generator resolves the configuration through the run's scope with the container as the fallback, the way the migrate commands and the framework's own runtime door read every service. A scope-level substitution of `service.config` was honoured by every other reader and silently ignored by `melody:cron:generate` alone
- `validation.go` — the user field is refused for any unicode space, the rule the schedule fields already read, rather than for the four ascii spellings alone. A user carrying a vertical tab, a form feed or a no-break space passed validation and was rendered into the user column beside those fields — where crond splits the line on it exactly as it splits on a plain space, so the entry either failed the daemon's user lookup and silently never ran, or shifted the column boundary and handed part of the name to the shell as the command. The heartbeat user goes through the same door.
- `runner_command.go` — the abandon timer is armed with a saturating sum of the entry's timeout and its graceful window. Both are caller-supplied and unbounded, so the natural spelling of "never abandon this one" — a graceful window written as the largest duration — overflowed into a negative delay, and a timer armed with one fires at once: every run of that entry was killed the instant it started, its container scope closed under it, and reported as having ignored a cancellation it never received.
- `runner_command.go` — the abandoned-run error names the window the run was actually given rather than the runner default. An entry that set its own `GracefulTimeout` produced a warning naming its window and an error naming a different one, and the error is the piece an operator reads out of the aggregated dispatch failure.
- `runner_command.go` — a command that returned in the same instant its abandon timer fired reports its own outcome instead of the kill. The two channels are both ready at that point and a select picks between ready cases at random, so a run that had already answered — with a success, or with its own failure — was reported abandoned, its result discarded, and the scope announced as closed under code that had already returned.
- cron: the in-process runner's kubernetes dialect now accepts a whole-field `?` in a day field, reading it as the wildcard with its star bit intact the way the robfig scheduler behind a CronJob manifest does. The dialect and its day rules already shipped here, and its documentation names the k8s template as the scheduler it follows, but the matcher refused `?` through the numeric parse — so a Quartz-conventional `Schedule{DayOfMonth: "?"}` panicked `NewRunnerCommand` at boot on a configuration the cluster runs happily. The crontab dialect and the zero value keep rejecting it, as crond has no `?`

## [v2.4.0] - 2026-07-17 - In-Process Cron Runner

### Added

- `runner_command.go`, `schedule_matcher.go` — `NewRunnerCommand(configuration, dialect, commands...)` adds an in-process scheduler command `melody:cron:run`: it parses the same five-field `Schedule` the generator renders and invokes each registered command when its schedule is due, so a single-binary deployment with no external crontab or kubernetes drives its scheduled work from the one `Configuration` that already feeds the generator. Each command is dispatched through the cli library with its declared flags — unset flags read their declared defaults, `CommandContext.Writer`/`ErrWriter` are usable and `Args()` is initialized, the same surface a command sees under the cli entry point — on a fresh scope and a cancellable child context; a failing or panicking job is logged (a scope-close failure joined onto its error) and the loop continues. Entries sharing a minute run concurrently, each in its own goroutine — like crontab starting an independent process per entry — so one slow job
  delays neither its minute-mates nor the scheduler loop; an entry that outlives its own interval therefore overlaps itself (wrap the command in a locker-backed exclusivity wrapper to serialize successive runs), and on shutdown the loop stops ticking and waits for in-flight jobs, whose contexts derive from the runtime context. The loop evaluates the minute its timer was armed for and reconciles wall-clock jumps with the vixie virtual-time algorithm: after a forward jump of less than three hours (daylight-saving spring-forward, suspend, ntp step) fixed-time entries — those pinning both minute and hour — catch up exactly once for every skipped wall minute while wildcard entries resume at the current minute; after a backward jump of less than three hours (daylight-saving fall-back) wildcard entries keep running every minute while fixed-time entries are suppressed for the repeated span; a jump of three hours or more re-anchors to the current minute without catch-up and logs the reset. The
  day-of-month / day-of-week combination follows a configurable dialect, `ModuleConfig.RunnerDialect` (second argument of `NewRunnerCommand`): the default `RunnerDialectCrontab` — also the zero value — follows vixie crond, whose day-star flag reads just the field's first character, so a star-based day field (the plain or the stepped wildcard, e.g. `*/2`) counts as unrestricted and the day fields combine with *and*, firing `0 0 */2 * 1` only on odd-numbered Mondays; `RunnerDialectKubernetes` follows the robfig scheduler behind the k8s template, where only the shapes the robfig star bit survives — the plain `*` and the unit-stepped wildcard, alone or inside a list — are unrestricted, so a stepped wildcard day field with a step above one stays restricted and combines with *or*, firing on any odd day or any Monday; the kubernetes dialect also bounds day of week at 6, as robfig does, so the Sunday alias `7` fails at construction instead of rendering a CronJob manifest the cluster rejects.
  Two genuinely restricted day fields combine with *or* in both dialects — the dialect changes only how a star-based field is classified — and the divergence on the star-based shapes is inherent to the two target schedulers, so pick the dialect of the manifests the same `Configuration`
  generates. A value naming no known dialect panics at construction with the new `ErrUnknownRunnerDialect`. Construction panics with `ErrUnsupportedRunnerEntry` when the shared `Configuration` contains an entry the runner cannot honor — a custom argv (`EntryConfig.Command`) or more than one instance — with the new `ErrDuplicateRunnerCommand` when two supplied commands share one name, since keeping the later one would silently drop the other (an exclusivity wrapper over its wrapped command, most likely), and with the new `ErrSharedRunnerCommandFlags` when a command returns the same flag instances on every `Flags()` call, since the cli library writes parse state into the instances and the runner's overlapping invocations would race on them. An entry that names a system user (`EntryConfig.User`) stays runnable — in-process every job runs as the process user — and `Run` logs one warning naming the affected commands, so the one `Configuration` keeps driving both the generated manifests and
  the runner. The schedule parser rejects a field carrying whitespace of any kind — leading, trailing or embedded, a no-break space or a vertical tab included. Embedded whitespace is the correctness case: crond splits the line on it and then refuses the whole crontab with a parse error, dropping every entry in the file (measured against vixie crond, which fails alike on an ascii space, a vertical tab and a no-break space); leading and trailing whitespace crond tolerates, and is refused only because the generator always has and the two halves are one rule. The parser also rejects a sign-prefixed number (`"+5"`, which `strconv` accepts and crond does not) and a step on a single value (`"5/15"`) — the one shape no two target schedulers agree on: vixie crond rejects it as a bad field and refuses the entire crontab, taking every other entry in the file down with it, busybox crond accepts it, and the robfig scheduler behind the k8s template reads it as the range from that value up — so
  neither half picks a meaning. The generator's field validation was widened to the same whitespace rule and now rejects the stepped single value too (new `ErrSteppedSingleValue`, naming the unambiguous rewrite: `"5-59/15"`), so the two halves are one rule and a schedule that runs in-process always generates. A step wider than the field is clamped to the field's cardinality rather than rejected, matching crond (whose expansion strides past the high bound on the first hop, so only the range's low value fires) while keeping a step near the integer maximum from overflowing the expansion loop into values the range never allowed. A scheduled command whose error carries an exit code is returned as a plain failure instead of reaching the cli library's default handler, which calls `os.Exit` and would take the whole scheduler down with the one job; the loop's chain anchor and first armed minute derive from one clock read, so startup cannot manufacture a phantom jump that skips the first minute
  for wildcard entries; and a wake that re-arrives at the wall minute the previous wake already dispatched is skipped, since a backward wall step inside the armed window makes the loop arm for that minute a second time and every wildcard entry would otherwise run twice seconds apart (the repeated wall minute of a fall-back is a different case — a whole hour of other minutes runs in between — and still fires). `--once` evaluates every schedule against the current time, runs the due commands and exits. Multi-instance safety is composed in — wrap a command in a distributed-lock exclusivity wrapper, or gate the whole runner behind a leader gate, before listing it (the melody/v3 `lock` package ships both; this major has no `lock` package, so the wrapper is composed in userland). Enable it through `ModuleConfig.RunnerCommands`.

## [v2.3.0] - 2026-07-11 - User-less Crontab Template

### Added

- `template_crontab.go`, `template.go` — new built-in template `crontab-no-user`: the user-less crontab dialect for busybox crond (alpine images) and per-user `crontab` files, which reject the `/etc/cron.d` user column the default `crontab` template emits — previously consumers cut the column with `sed` in the image build. Select it with `--template=crontab-no-user` or the `melody.cron.template` parameter; the user parameter/flag is ignored entirely in this dialect, everything else — schedules, log redirects, heartbeat, validation — is identical. Back-port from `v3`.

### Fixed

- `generate_command.go` — `melody:cron:generate` no longer aborts with `ErrHeartbeatUserMissing` when a heartbeat is configured for the `crontab-no-user` template. That template renders no user column (busybox crond, per-user crontab deployments), so a heartbeat had no user column to attach to and the pre-render check rejected an otherwise valid configuration.
